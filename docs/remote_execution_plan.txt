

ACP 远程计算节点支持 — 详细开发计划

概述

为 ACP 平台添加远程计算节点支持，使 ACP Server 能通过 SSH/SFTP 将完整的 acp 作业提交到远程 OpenLAVA (LSF) 节点执行，并通过 LSF 日志实时监控状态。远程节点无需手动安装 ACP，代码通过 CodeSyncer 自动同步（SFTP 增量传输），支持所有工作流（conformer / nmr / mechanism / benchmark）。

核心约束

 | 远程节点环境 | Python ≥ 3.10 + rdkit/numpy/openpyxl/pyyaml + OpenLAVA (LSF) + QC 软件齐全（Gaussian/ORCA/xTB/CREST）

 | 代码部署 | CodeSyncer 自动同步：SFTP 增量传输 src/acp/（排除 api/scheduler）+ src/cccp/ + scripts/ 到 {remote_code_dir}/，无需 pip install

 | CLI 入口 | python -m acp.cli run <workflow>（LSF 脚本设置 PYTHONPATH={remote_code_dir}/src）

 | 执行粒度 | 整个 acp.cli run <wf> 命令作为一个 LSF 作业

 | 工作流范围 | 所有工作流（conformer / nmr / mechanism / benchmark / fake）

 | 文件系统 | 输入通过 SFTP 上传，所有结果保留在远程节点，不自动下载任何计算文件，仅支持用户按需单文件下载

 | 监控方式 | LSF bjobs 状态 + SFTP 增量 tail stdout.log/stderr.log（不依赖 state.json）

 | 轮询间隔 | 30 秒

 | QC 配置 | 远程节点自行配置 ~/.cccp.yaml 或环境变量，不同步本地 config/defaults.yaml

 | 多节点 | 支持多个远程计算节点，负载最低优先选择

 | 远程文件保留 | 180 天

步骤 1.4：实现 SSH 连接池（线程安全） ✓ 已完成

线程安全：queue.Queue 租借/归还模式，每节点连接数 = max_concurrent_jobs（从 RemoteNode 配置读取）

paramiko SSHClient 非线程安全，JobManager 用 ThreadPoolExecutor，必须隔离

execute(cmd) -> (exit_code, stdout, stderr)，自动重连（2 次重试）

密码/密钥双认证，日志脱敏（不输出密码/密钥内容）

步骤 1.6：实现 CodeSyncer（代码自动同步） ✓ 已完成

新建 sync.py — CodeSyncer

sync_code(node, ssh_pool) — 同步代码到远程节点 {remote_code_dir}/

check_sync_needed(node) -> bool — 检查本地代码是否有变更（基于本地 mtime 记录比较）

同步内容：
  
  
src/acp/（排除 api/、scheduler/ 子目录）— 执行路径不依赖这两个模块
  
src/cccp/（完整）— acp 委托给 legacy 包执行 QC 计算
  
scripts/run_g16_worker.sh — Gaussian 包装脚本
  

不同步：config/defaults.yaml（QC 路径远程不同，由远程节点自行配置）

不同步：frontend/、tests/、pyproject.toml、bin/

同步策略：本地记录每个文件的 mtime，同步时比较"本地当前 mtime vs 本地上次同步时 mtime"，若变化则上传。远程 mtime 不参与判断（SFTP 上传后远程 mtime 会变成上传时间，不可靠）。首次同步较慢，后续快速

远程目录结构：
{remote_code_dir}/
  src/
    acp/          # cli.py, core/, backends/, chem/, io/, workflows/, nmr/, reports/
    cccp/  # 完整 legacy 包
  scripts/
    run_g16_worker.sh

新建 runner.py — 完整远程执行流程

[新增] 检查/同步代码到选定节点（若 auto_sync=True 且代码有变更，调用 CodeSyncer.sync_code()）

不下载任何文件 — 远程结果保留在远程节点

完成后处理：

record.exit_code = .exit_code 值

record.result = {lsf_job_id, node, remote_dir, exit_code} — LSF 元数据

Provenance 从 CLI 命令行 + LSF 元数据构建，不调用 _capture_artifacts

创建简化 remote_execution stage task：状态跟随 LSF 状态更新（PEND→RUNNING→DONE/FAILED），前端可显示"远程执行: PEND/RUN/DONE"

下述回归测试不包含本地 CCO 搜索——所有 QC 验证在远程节点进行

根因

ACP Server 的 src/cccp/ 是一个分叉版本，与计算节点 /home/<user>/cccp/ 的权威版本存在结构性差异。CodeSyncer 将 ACP Server 的分叉版本同步到远程节点的 {remote_code_dir}/src/cccp/，LSF 脚本的 PYTHONPATH={remote_code_dir}/src 使同步版本在 import 优先级上覆盖了远程节点本地安装的权威版本（原始文件未受影响），导致：

协议不匹配：ACP 版本无 lite/zero/benchmark 协议 → _validate_config 回退为 ext，输出 warning

DFT 阶段跳过：ACP 版本的 ConformerEngine（1280 行）在 ISOSTAT 聚类后直接 finalize，不调用 _run_shared_dft_handoff。远程权威版本（1733 行）的引擎在聚类后继续执行 DFT 优化/频率/单点/Shermo

API 不兼容：acp/cli.py 依赖 cccp.core.specs.ConformerWorkflowSpec（ACP 独有），远程版本使用 cccp.core.protocols.ProtocolSpec（不同 dataclass 设计）

步骤 4.1：RemoteResultFetcher ✓ 已完成

新建 remote/fetcher.py — RemoteResultFetcher（196 行）

is_remote_job(record) -> bool — 检查 record.result 是否含 node + remote_dir

resolve(record) -> (RemoteNode, str) — 从 record.result 提取节点名 + 远程目录，通过 RemoteExecutionConfig.get_node() 解析为 RemoteNode。无元数据抛 NotARemoteJobError，节点未配置抛 RemoteFileError

list_files(record) -> list[RemoteFileInfo] — SFTP 列远程作业目录（顶层）

file_exists(record, filename) -> bool — SFTP stat 检查文件是否存在

read_file(record, filename) -> bytes — SFTP 读取完整文件（中小文件）

stream_file(record, filename) -> Iterator[bytes] — SFTP 分块流式下载（64KB chunks），借连接池会话期间持有，迭代结束自动归还。大文件不占满内存

log_tail(record, log_name, lines=100) -> str — 从文件末尾读最多 4MB，取最后 N 行。读取起点 max(0, size - 4MB)；若截断了首行则丢弃不完整行

_safe_join(remote_dir, filename) — 路径拼接 + 遍历防护：posixpath.normpath 后校验结果仍在 remote_dir 下，../../etc/passwd 等逃逸路径抛 RemoteFileError

设计要点：复用 RemoteJobRunner 同一个 SSHConnectionPool + FileStager，SSH 连接跨执行与检索共享。JobManager._create_remote_runner() 构造 RemoteResultFetcher 并存入 self._remote_fetcher，通过 manager.remote_fetcher 属性暴露给 API 层。

自定义异常：RemoteFileError（基类）、NotARemoteJobError（非远程作业）

步骤 4.2：扩展 API 端点 ✓ 已完成

修改 api/v1_routes.py（+3 端点 +2 辅助函数）+ api/v1_schemas.py（+3 schema）

GET /jobs/{id}/remote-files — 列出远程作业目录（顶层）。返回 RemoteFileListResponse（job_id / node / host / remote_dir / files[]）。目录不存在 → 404；SSH 失败 → 502

GET /jobs/{id}/remote-files/{file_path:path} — 流式下载单个文件（支持嵌套子目录路径如 finalDFT/sp.out）。先 stat 确认存在（404 不存在），再 StreamingResponse 分块输出，Content-Disposition: attachment。路径遍历 → 400

GET /jobs/{id}/remote-logs/{name} — 获取日志尾部（stdout.log / stderr.log，?lines=N 默认 100 上限 5000）。非法 log 名 → 400

新增 schema：RemoteFileEntry（name/size/mtime/is_dir）、RemoteFileListResponse（含 node/host/remote_dir 元数据）、RemoteLogTailResponse（job_id/name/lines[]）

错误码映射：FileNotFoundError→404（清理后）、RemoteFileError→400（路径遍历/非远程作业）、其他 SSH 异常→502。非远程作业调用 → 400（提示用 /jobs/{id}/files）。远程未配置 → 503

说明：前端根据作业是否为远程，分别调用 /jobs/{id}/files（本地）或 /jobs/{id}/remote-files（远程）。V1JobRecordModel.result 含 node/remote_dir 字段，前端可据此判断。

✅ 优点

复用既有 SSH 池：fetcher 与 RemoteJobRunner 共享同一 SSHConnectionPool + FileStager，无额外连接开销，线程安全由池保证

路径遍历防护：_safe_join() 用 posixpath.normpath + 前缀校验，../../etc/passwd 和绝对路径 /etc/shadow 均被拦截并返回 400

流式下载不占满内存：stream_file 64KB 分块 yield，借 sftp_session 上下文管理器，迭代结束自动归还连接。10.16.5.157 真实下载 CCO_remote_v2_global_min.xyz（541B）和 submit.lsf（587B）验证通过

日志尾部高效：仅读末尾 4MB（_LOG_TAIL_MAX_BYTES），从 max(0, size - 4MB) seek，截断首行丢弃不完整行。GB 级日志不爆内存

错误码语义清晰：404（文件/目录不存在或已清理）vs 400（客户端错误：路径遍历/非远程作业）vs 502（SSH/SFTP 网络失败）vs 503（远程未配置）分层

嵌套子目录下载：{file_path:path} 转换器支持 finalDFT/sp.out 等多级路径，与本地 /jobs/{id}/files/{file_path:path} 一致

遵循项目约定：PEP 604 注解、from __future__ import annotations、Google-style docstring、__all__ 导出、模块级 logger、frozen 无关（无 dataclass）

JobManager 惰性集成：remote_fetcher 属性仅在远程启用时构造，本地模式返回 None，API 返回 503 不崩溃

步骤 5.1：RemoteCleanup 模块 ✓ 已完成

新建 remote/cleanup.py（429 行）— RemoteCleanup + CleanupReport + HousekeepingDecision

cleanup_old_jobs(node, retention_days=None, dry_run=False, max_dirs_per_sweep=100) -> CleanupReport — 扫描 node.remote_work_dir 顶层目录，递归删除（rm -rf over SSH）mtime 早于 retention_days 的子目录。配置默认 180 天，可按调用覆盖。max_dirs_per_sweep 封顶单次清理量（每目录 2 次 SSH 往返：du+rm），默认 100，0 无限制，剩余下次继续

pre_submit_housekeeping(node) -> HousekeepingDecision — 提交前磁盘压力检查：
  
  
磁盘 ≤ DISK_CLEANUP_THRESHOLD（90%）→ 无操作，继续提交
  
磁盘 > 90% → 触发 cleanup_old_jobs 清理，然后复查
  
磁盘 > DISK_SKIP_THRESHOLD（95%）（清理后仍超）→ should_skip=True，节点被拒绝
  
after-probe 保守回退（审计 P1-1 修复）：若 before 已知高压但 after 探测失败（返回 0），回退到 before 值而非 fail-open，避免掩盖满盘
  

仅管理顶层目录：顶层散落文件（非 job 子目录）保持不动；remote_work_dir 本身及祖先目录永不删除

安全防护：_is_safe_work_dir() 拒绝 /、.、..、~、相对路径、单层绝对路径（如 /scratch），防御配置错误

fail-open 策略：磁盘查询失败（SSH 抖动）返回 0%（继续提交，不阻断）；cleanup_old_jobs 内部错误按目录记录到 report.errors 不抛异常

freed_bytes_est：删除前通过 du -sb 估算释放字节数（GNU coreutils），检查退出码（审计 P2-1 修复），失败回退为 0 并记录 debug 日志（审计 P2-2 修复）

dry_run：填充 report 但不删除，供未来手动清理 API 预览；汇总日志含 dry-run 标记（审计 P2-4 修复）

数据类：

@dataclass
class CleanupReport:
    node: str
    retention_days: int
    removed_dirs: list[str]      # 已删除（或 dry_run 下将删除）的远程路径

    @property
    def ok(self) -> bool: ...    # errors 为空时 True

@dataclass
class HousekeepingDecision:
    node: str
    should_skip: bool            # True → 调用方拒绝该节点
    disk_usage_before: int       # 清理前磁盘百分比

6B. 阶段 5B：本地磁盘保护（ACP Server 端）

Phase 5 仅保护了远程计算节点的磁盘。ACP Server 本地的 run_root（作业 work_dir + SQLite DB + 事件日志）无任何清理和保护——作业无限堆积，磁盘满时 OSError 被 bare except Exception 静默吞掉。本阶段为本地文件系统增加与 Phase 5 对等的生命周期管理。

现状缺口

 | 本地 work_dir | 每个 job 的 events.jsonl / job.json / inputs/ 永久保留，无 TTL、无 retention、无定时清理

 | SQLite acp_jobs.db | 已完成/失败 job 记录无限堆积（scheduler/AGENTS.md 已标记为已知问题）

 | 本地 JobRunner | 提交前不检查磁盘，直接 mkdir + 跑子进程；磁盘满时静默崩溃

 | 无 DELETE /jobs/{id} | 只能删整个 project（DELETE /projects/{id}?delete_data=true），无法删单个 job

 | 运行模式 | 纯远程调度——本地 work_dir 仅元数据（KB-MB 级），但 SQLite + 事件日志持续膨胀

 | 当前部署 | ACP_RUN_ROOT=/tmp/acp_runs（tmpfs 923M，62% 已用），重启即清空——生产环境应迁到持久卷

两级保留策略（用户确认）

 | 对象 | 保留期 | 策略

 | work_dir（completed） | 30 天 | mtime + DB 状态判定，到期删除整个 job 目录

 | work_dir（failed） | 90 天 | 失败作业保留更久，便于排查

 | work_dir（cancelled） | 30 天 | 同 completed

 | SQLite DB 记录 | 365 天 | 独立于 work_dir——work_dir 删除后 DB 记录仍可查询历史；到期后删除 DB 行 + 可选 VACUUM

 | 孤儿目录（DB 无记录） | 30 天 | 按 completed 策略兜底清理

说明：work_dir 先于 DB 记录过期（30/90 天 vs 365 天），存在一个窗口期——DB 记录存在但 work_dir 已删。API 的文件端点已能优雅处理此情况（返回 404 "work_dir not found"），历史查询仍可从 DB 获取元数据。

三种触发机制（用户确认全部需要）

 | 1. 提交前检查 | 本地 JobRunner 提交前检查 shutil.disk_usage(run_root)：>90% 触发清理，>95% 拒绝提交（同 Phase 5 远程设计）

 | 2. 后台定时清理 | 独立 daemon 线程，每 cleanup_interval_hours（默认 6h）扫描 run_root + SQLite，不依赖提交触发

 | 3. 手动 API 端点 | POST /api/v1/maintenance/cleanup 供运维手动触发 + ?dry_run=true 预览

状态判定逻辑（一次 DB 查询 + 文件系统遍历）：

# 1. 查 DB 构建 {job_id: (status, completed_at)} 映射
status_map = {r.id: (r.status, r.completed_at) for r in store.list(limit=100000)}

# 2. 遍历 run_root/{project_id}/{job_id}/
for project_dir in run_root.iterdir():
    for job_dir in project_dir.iterdir():
        job_id = job_dir.name
        status, completed_at = status_map.get(job_id, (None, None))
        # 3. 按状态选保留期
        if status == 'failed':
            retention = policy.failed_days      # 90
        else:
            retention = policy.completed_days    # 30（含 completed/cancelled/孤儿）
        # 4. mtime + completed_at 取较新者判定过期
        age_ref = completed_at or _iso_to_epoch(job_dir.stat().st_mtime)
        if now - age_ref > retention * 86400:
            shutil.rmtree(job_dir)

    while not stop_event.wait(interval):
        try:
            report = self._local_cleanup.full_cleanup()
            self._write_cleanup_log(report)
        except Exception:
            logger.warning("Background local cleanup failed", exc_info=True)

当前 ACP_RUN_ROOT=/tmp/acp_runs 是 tmpfs——重启即清空所有 job 数据。生产环境应迁移到持久卷（如 /var/lib/acp/runs），否则本地清理策略无意义（tmpfs 随内存压力自动驱逐）

tmpfs 容量 = 物理内存的一部分（当前 923M），大量 job 元数据可能挤占计算进程内存。迁移到磁盘卷后此问题消失

systemd 服务需更新：Environment=ACP_RUN_ROOT=/var/lib/acp/runs + LogsDirectory / StateDirectory 声明

权限：/var/lib/acp/runs 属主 <user>:<user>，systemd 服务已以该用户运行

def _cleanup_loop(self, stop_event: threading.Event):
    # 首次随机延迟，避免多实例同时触发
    first_delay = random.uniform(0, interval)
    if stop_event.wait(first_delay):
        return
    while not stop_event.wait(interval):
        if not self._cleanup_lock.acquire(blocking=False):
            continue  # 上一轮还在跑，跳过
        try:
            report = self._local_cleanup.full_cleanup()
            self._write_cleanup_log(report)
        except Exception:
            logger.warning("Background local cleanup failed", exc_info=True)
        finally:
            self._cleanup_lock.release()

14. 实施注意事项

14.1 远程节点一次性准备

Python ≥ 3.10

依赖安装：pip install rdkit numpy openpyxl pyyaml

QC 软件：Gaussian 16, ORCA, xTB, CREST（路径在 ~/.cccp.yaml 或环境变量中配置）

OpenLAVA (LSF) 客户端

无需安装 ACP — 代码由 CodeSyncer 自动同步到 {remote_code_dir}/

14.2 代码同步策略

同步内容：src/acp/（排除 api/、scheduler/）+ src/cccp/（完整）+ scripts/run_g16_worker.sh

不同步：config/defaults.yaml（QC 路径远程不同，避免覆盖远程配置）

不同步：frontend/、tests/、pyproject.toml、bin/

增量同步：本地记录每个文件的 mtime，同步时比较"本地当前 mtime vs 本地上次同步时 mtime"，若变化则上传。远程 mtime 不参与判断（SFTP 上传后远程 mtime 会变成上传时间，不可靠）。首次同步较慢，后续快速

远程 PYTHONPATH：LSF 脚本设置 export PYTHONPATH={remote_code_dir}/src:$PYTHONPATH，无需 pip install

14.3 日志阶段解析（分阶段实施）

基础版本（阶段 1-8）：仅依赖 bjobs 状态 + .exit_code，日志 tail 仅作为原始文本展示，不做阶段解析。

增强版本（阶段 9）：实现 LogStageParser，通过正则匹配日志中的阶段标志行，更新 stage task 子阶段状态。具体标志行需要在远程节点配置完成后，通过实际运行作业验证。

14.4 安全

密码仅通过环境变量传递，YAML 中不存储明文密码

SSH 日志脱敏：不输出密码、密钥内容

远程文件保留 180 天后自动清理

14.5 StageTaskObserver 集成

远程作业创建简化的 remote_execution stage task，状态跟随 LSF 状态更新：

PEND → pending

RUN → running

DONE → completed

EXIT → failed

前端可显示"远程执行: PEND/RUN/DONE"，提供基本的进度反馈。

14.6 作业取消策略

发送 bkill <lsf_job_id> 后检查返回值：

返回 0：取消成功

返回非 0：取消失败（可能作业已结束），记录日志但不抛异常

 | 问题 | 选项 | 决策 | 理由

 | server.py 配置注入方式
 | A) create_app() 内部加载
B) 扩展 create_app() 签名
 | A
 | 改动最小，与现有环境变量读取模式一致，配置加载失败可降级

 | StageTaskObserver 处理
 | A) 完全跳过
B) 创建简化 remote_execution stage
 | B
 | 前端可显示进度，/api/v1/jobs/{id}/tasks 不返回空

 | SSH 连接池大小
 | A) 固定 3 个连接
B) 连接数 = max_concurrent_jobs
 | B
 | 避免 max_running > 3 时连接等待，更灵活

 | 日志阶段解析策略
 | A) 同时实现日志解析
B) 先基础版本，日志解析最后增强
 | B
 | 日志格式需验证，先确保基础功能稳定

 | 代码同步增量策略
 | A) size + mtime
B) size + content hash
C) 本地 mtime 记录
 | C
 | 远程 mtime 不可靠（SFTP 上传后改变），本地记录更准确

 | 远程作业取消策略
 | A) bkill 后立即返回
B) bkill 并检查返回值
 | B
 | 更健壮，可记录失败情况

 | 磁盘清理触发时机
 | A) 后台定时任务主动清理
B) 提交前按需触发（disk > 90%）
 | B
 | 无需额外进程/timer；低压力时不浪费 SSH 往返；高压时一次性清理足够（180 天保留 + 突发提交场景下旧目录数有限）。定时主动清理留待 Phase 6+ 增强

 | housekeeping 失败模式
 | A) 任何失败均阻断提交
B) 瞬时错误 fail-open / 明确决策 fail-closed
 | B
 | SSH 抖动（df 查询失败）fail-open 避免误伤；明确 disk > 95% fail-closed 避免 ENOSPC 中断。两类失败模式分层处理

 | 节点满载时的处理
 | A) 自动尝试下一节点
B) 抛 RemoteNodeUnavailableError 让作业失败
 | B
 | housekeeping 仅针对已选节点（避免对每个候选 df 查询）。重试时 least_loaded 自然选到其他节点。Phase 6 可在 _select_least_loaded 融合磁盘检查实现自动故障转移
