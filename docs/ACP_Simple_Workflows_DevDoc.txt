5.5 Stage 间数据传递链（optfreqsp 关键设计）

optfreqsp 的管线涉及三个 stage，每个 stage 的输出需要作为下一 stage 的输入。数据流如下：

 ingest (结构文件)
   │
   │  coordinates, symbols, charge, multiplicity
   ▼
 opt_freq (ORCA Opt Freq)
   │
   │  ├─ coordinates （优化后坐标）→ 传给 single_point
   │  ├─ energy （优化能量）
   │  ├─ frequencies （频率列表）
   │  └─ log_file （ORCA .out 路径）→ 传给 shermo
   ▼
 single_point (ORCA SP, 使用 opt_freq 输出的坐标)
   │
   │  ├─ energy （高精度单点能）
   │  └─ log_file
   ▼
  shermo (读取 opt_freq 的 log_file 计算热化学修正)
    │
    │  ├─ zpe, enthalpy, gibbs_correction, entropy
    │  └─ gibbs_correction → 传给 finalize（不含 SP energy）
    ▼
  finalize (SP energy + gibbs_correction → 最终自由能 → thermo.json)

实现要点：

simple.py 内部维护一个 context: dict[str, Any] 在 stage 间传递中间数据，包括 opt_coords, opt_log_path, sp_energy 等。

Shermo 阶段调用实际位于 cccp.qc.runners.run_shermo()，通过 acp.backends.external 重导出（external.py:3，__all__ 包含 run_shermo）。调用路径：from acp.backends.external import run_shermo。传入 opt_freq 的 log 文件路径。Shermo 只输出热化学修正值（gibbs_correction, zpe, enthalpy, entropy），不含单点能。

finalize 阶段手动计算最终自由能：free_energy = sp_energy + shermo_gibbs_correction（Shermo 默认以输入 log 的电子能量为参考，而 opt_freq 的电子能量精度低于 SP 级别，因此必须替换为 SP energy）。

⚠️ 单位转换（Critical）： Shermo 默认输出热化学修正值单位为 kcal/mol，而 ORCA SP energy 单位为 Hartree。finalize 阶段必须调用 acp.core.models.HARTREE_TO_KCAL（或 cccp.utils.constants.HARTREE_TO_KCAL）将 SP energy 转换为 kcal/mol 后求和，或在自由能输出时统一为 Hartree。两个模块均定义了该常量（v4.0 审查确认），但注意两处值一致（627.509 kcal/mol）。建议 finalize 使用 from acp.core.models import HARTREE_TO_KCAL。

method_levels_to_workflow_config() 对非 confsearch schema 直接返回 dict(levels)，simple.py 收到后将三层 levels 分别路由到对应的 backend 调用（orca → opt_freq, orca → single_point, shermo → thermochemistry）。

--nproc / --maxcore 从 CLI 参数传入后，通过 **kwargs 透传到 ORCABackend → ORCAInterface。ORCAInterface 已有 _build_input_blocks() 将其写入 %maxcore 和 %pal nprocs 块（通过 pal_settings 和 maxcore 参数）。simple.py 的 handler 需显式提取 nproc 和 maxcore 并作为 kwargs 传入 ORCA backend：orca_kwargs = {}
if nproc:
    orca_kwargs["pal_settings"] = f"nprocs {nproc}"
if maxcore:
    orca_kwargs["maxcore"] = maxcore
result = backend.opt_freq(coords, symbols, charge=charge, multiplicity=mult, output_dir=out_dir, **orca_kwargs)

5.6 错误处理策略

各 stage 的错误处理遵循以下规则：

 | 场景 | 行为 | 说明

 | 输入文件格式不支持 | 抛出 ValueError（含支持的格式列表） | 在 handler 最外层捕获，统一通过 CLI/scheduler 报告给用户

 | ORCA 子进程非零退出 | 读取 ORCA .out 文件末尾错误信息，封装为 RuntimeError 抛出 | 不吞异常；scheduler 将 job 标记为 failed 并保留 .out 文件供排查

 | ORCA 输出频率解析失败 | 记录 warning log（frequencies 字段设为空列表，has_frequencies=False），继续执行 | 非致命错误：thermo/Shermo 阶段会因缺少频率而跳过

 | Shermo 二进制未找到 | optfreqsp 的 shermo stage 抛出 FileNotFoundError，终止管线 | 在 simple.py handler 中调用 shutil.which("shermo") 前置检查

 | optfreqsp 某中间 stage 失败 | 整个 job 失败，不执行后续 stage | 由 scheduler 的 job lifecycle 管理（manager.py），StagePlan 的 depends_on 字段确保顺序依赖

 | 输出目录冲突 | 自动追加 _1, _2... 唯一化 | 调用 _ensure_unique_dir()，无覆盖风险

def _ensure_unique_dir(base_dir: str | Path) -> Path:
    base = Path(base_dir).resolve()
    if not base.exists():
        base.mkdir(parents=True)
        return base
    counter = 1
    while True:
        candidate = base.parent / f"{base.name}_{counter}"
        if not candidate.exists():
            candidate.mkdir(parents=True)
            return candidate
        counter += 1

method_levels_to_cli_flags() 具体实现

在 catalog.py 中新增以下函数，供 _build_cmd() 及其它需要将 level 映射为 CLI 参数的模块调用：

_LEVEL_TO_CLI_FLAG_MAP: dict[str, str] = {
    "functional": "method",
    "basis": "basis",
    "aux_basis": "sp-aux-basis",
    "ri_approximation": "sp-ri-approximation",
    "dispersion": "dispersion",
    "solvent_model": "solvent-model",
    "solvent": "solvent",
    "temperature": "temperature",
    "pressure": "pressure",
    "scale_factor": "scale-factor",
    "max_steps": "geom-maxiter",
    "opt_convergence": "opt-convergence",
    "grid": "grid",
    "scf_convergence": "scf-convergence",
}

def method_levels_to_cli_flags(
    levels: dict[str, Any],
    prefix_map: dict[str, str] | None = None,
) -> list[str]:
    """Convert method levels dict to CLI flag list.

    Args:
        levels: Nested dict - e.g. {"optfreq": {...}, "single_point": {...}}.
        prefix_map: level_id → CLI flag prefix (default: no prefix for all).

    Returns:
        CLI flag list - e.g. ["--method", "wB97M-V", "--basis", "def2-TZVPP"].
    """
    prefix_map = prefix_map or {}
    cmd: list[str] = []
    for level_id, level_config in levels.items():
        prefix = prefix_map.get(level_id, "")
        for field, value in level_config.items():
            if field == "engine" or value is None or value == "":
                continue
            cli_flag = _LEVEL_TO_CLI_FLAG_MAP.get(field)
            if cli_flag is None:
                continue
            flag = f"--{prefix}{cli_flag}"
            cmd += [flag, str(value)]
    return cmd

用法示例（_build_cmd 中）：

from acp.catalog import method_levels_to_cli_flags

# optfreqsp 的 prefix_map：optfreq 无前缀，single_point 使用 --sp- 前缀
prefix_map = {"optfreq": "", "single_point": "sp-", "thermo": ""}
cmd += method_levels_to_cli_flags(levels, prefix_map)

optfreqsp 的 single_point level 覆盖语义： 当前附录只说"后者优先"，但未给出具体实现模式。建议在 _build_cmd() 中先为 optfreq level 生成 CLI flags，再为 single_point level 生成（使用 --sp- 前缀），最后合并时 single_point 的非空字段覆盖 optfreq 的同名字段（如 solvent/dispersion）。两个字段集不冲突（前缀不同），覆盖通过 optfreqsp handler 内部参数合并实现。

CLI 直调 vs scheduler 路径的参数对齐： 当前 _add_simple_workflow_args() 直接调用时不含 --config 参数，但 scheduler 的公共参数段（runner.py:721-730）会加 --config。建议在 _add_simple_workflow_args() 中也加入 --config（optional），确保两条路径的参数集合一致。

Shermo 输出模式确认： Shermo 的 -mode 参数决定输出是绝对热化学量还是修正值。需确认 run_shermo() 调用时使用的 mode。若 Shermo 输出了绝对 Gibbs 自由能（含 opt_freq 级别的电子能量），则 finalize 阶段不需要手动加 SP energy，只需替换电子能量部分。建议实施前验证 run_shermo() 的调用参数和输出格式。

optfreqsp 的频率和热化学输出： 当前设计在 opt_freq 阶段解析频率，Shermo 阶段读取 opt_freq 的 log 计算热化学修正。但 Shermo 可能输出绝对热化学值（以输入 log 的电子能量为参考）。需要确认 Shermo 的输出中 gibbs_correction 是否确实为"修正值"（即不含电子能量），还是包含电子能量的绝对 Gibbs 值。若是后者，finalize 阶段应使用 free_energy = sp_energy + (shermo_gibbs - opt_freq_energy) 而非 sp_energy + shermo_gibbs_correction。

多个 level 间 engine 冲突检测： optfreqsp 的 optfreq 和 single_point level 各自指定 engine，理论上可以是不同 engine（如 ORCA 做 Opt+Freq，Gaussian 做 SP）。当前假设均为 ORCA，但 schema 设计允许不同。建议在 handler 中增加 engine 一致性检查，若不一致则报错（直至多 engine 支持实现）。

14.2 Critical 隐患（已修复 ✅）

v7.5 中已全部修复。详见 §15 v7.5 修复详情。

C1 — scheduler 预创 work_dir 导致 ensure_unique_dir 偏移，所有输出落入错误目录 已修复

⚠️ 影响范围： 所有 simple 工作流通过 scheduler 提交时，输出写入 work_dir_1/ 而非 work_dir/。scheduler 的 _monitor、_capture_artifacts、StageTaskObserver 全部监控 work_dir/——所有输出、进度追踪、artifacts、provenance 全部丢失。

根因链：

JobRunner.run() 第 410 行预创建 work_dir.mkdir(parents=True, exist_ok=True)

_build_cmd() 第 718 行将同一目录传入 --output CLI 参数

simple.py 所有入口函数第一件事是调用 ensure_unique_dir(output_dir)

ensure_unique_dir（core/utils.py:8）先尝试 mkdir(exist_ok=False) → 因为目录已存在触发 FileExistsError → 进入 counter 循环 → 创建 work_dir_1/

✅ 修复方式（v7.5）： 新增 _resolve_output_dir() 函数，检测目录是否已存在且为空（scheduler 预创建），是则直接复用。否则调用 ensure_unique_dir() 创建唯一目录。所有入口函数已替换调用。

C2 — simple 工作流完全不生成 state.json / stage_tasks/*.json，scheduler 监控静默失效 已修复

关联文件： simple.py（全文件）vs runner.py:524-537、stage_tasks.py:313-316

simple.py 是纯过程式函数（接收参数 → 调用 ORCABackend → 返回 WorkflowResult），不使用 WorkflowState，不写 state.json，不写 stage_tasks/*.json。但 scheduler 的 StagePlanProvider 为每个 simple 工作流声明了 1-3 个 stage。结果：所有 StageTask 行保持在 "pending" 状态直到 job 结束，然后被批量标记为 "skipped"。用户看到 job COMPLETED 但每个 stage SKIPPED。

✅ 修复方式（v7.5）： 集成 WorkflowState，新增 _init_state() 辅助函数在入口函数开始时声明 stage、写入 state.json。计算执行前后调用 state.set_stage()/state.complete_stage()/state.fail_stage() 跟踪状态。完成后调用 state.mark_completed() 将 pending stage 标记为 skipped。scheduler 的 find_workflow_state() 现在能正确发现并读取进度。

新增 v8.0 · 2026-07-31

基于计算节点（10.16.5.157，用户 <user>）上真实运行的 ORCA/Shermo 产物进行逐行核对，验证样本：20260720_223201_001_optfreqsp（H₂O，optfreqsp 全流程）、20260721_135435_004_2-epi-curcusone-i（大分子 Opt Freq）。这是首次以真实 ORCA 5.x 输出对照代码解析逻辑——此前全部测试均基于 mock，无真实 log fixture。

18.1 结论 1（Critical）：频率解析正则 bug 已证实 —— 真实 ORCA 输出 0 匹配

⚠️ 影响：所有简单工作流的 frequencies.txt 均无法生成（生产 job 20260720_223201_001_optfreqsp 目录中确认无此文件）；n_frequencies=0、has_frequencies=False，仅一条 warning，静默降级。

真实 ORCA 5.x 频率行格式（orca_optfreq.out 第 5048 行起）：

VIBRATIONAL FREQUENCIES
-----------------------
Scaling factor for frequencies =  1.000000000  (already applied!)

   0:         0.00 cm**-1
   1:         0.00 cm**-1
   5:         0.00 cm**-1
   6:     -1190.82 cm**-1 ***imaginary mode***
   7:     -1177.02 cm**-1 ***imaginary mode***
   8:      1411.55 cm**-1

实际格式为    N:     value cm**-1（模式号 + 冒号前缀，虚频带 ***imaginary mode*** 后缀）

现有正则 Mode\#\s+\d+\s+:\s+([-+]?\d+\.\d+)\s+cm\*\*-1（orca.py:767/877）假设 "Mode #" 前缀——在真实输出上 findall 返回空列表

该正则随 v7.x 引入，从未对照真实输出验证；全库无真实 ORCA log fixture

18.2 结论 2（修复正则后的隐藏坑）：单个 Opt Freq log 含多个频率段

真实 orca_optfreq.out 中 VIBRATIONAL FREQUENCIES 段出现多次：H₂O 快速收敛 2 段；curcusone-i 共 4 段（行 5049 / 21151 / 37266 / 48183）。原因：Recalc_Hess 在优化过程中每次重算 Hessian 都会打印一组频率。

⚠️ 修复正则时若用 re.findall 全文件匹配，会把优化中间步骤几何的频率混入最终输出。正确做法：按 VIBRATIONAL FREQUENCIES 切段取最后一段，并过滤每段开头 6 个 0.00 平动/转动模式。
