## 3. 还需落到具体操作的修订

### R2-01：B08 不应在持有一个写事务时，含糊地调用另一个写连接

位置：[B08](../../../.omo/plans/acp2-parallel-plan-b-runtime.md#L250)、[B09](../../../.omo/plans/acp2-parallel-plan-b-runtime.md#L260)。优先级：高，在实施 B08 前确定。

新版要求 `create_with_idempotency` 从领取幂等键起持有 `BEGIN IMMEDIATE`，经过资源预留、目录分配直到 job 入库。现有 [ReservationLedger](../../../../src/acp_services/runtime/admission.py#L809) 会自行 `_connect()`，预留时自行执行 `BEGIN IMMEDIATE`；[JobStore](../../../../src/acp_services/store/store.py#L150) 也独立管理连接。

若两者共用一个 SQLite 文件，外层事务等待内层预留返回，而内层写连接等待外层释放锁，最后会超时失败。若用不同数据库，预留可以先提交，但不能再把未提交的幂等插入称为“第一个 durable step”。新增的四类崩溃验收是正确的，不能用一句“同一事务”代替连接与提交点设计。

建议在计划中明确选择一种：

1. 同库共享连接：事务边界内的 JobStore / 预留写入共用显式传递的 connection；内部不得再打开写连接。提交派发意图并 COMMIT 后才启动执行。
2. 分阶段协议：短事务持久化可恢复领取，预留、目录、job、派发分别有明确关联键和补偿；不跨独立写连接长期持锁。继续复用现有提交与恢复权威。

还要把方法入口与顺序对齐：当前 `create_with_idempotency(record, ...)` 接收已经构造的 JobRecord，需说明如何做到领取发生在目录分配前。可调整内部事务接口或延迟构造 record，不能仍让调用方先分配目录，再进入这个方法。

新增验收：按最终生产数据库布局运行两路真实连接的提交/预留，不能只测隔离的 store 方法；检查超时、回滚、预留回收，以及 job/派发意图提交前没有 QC 或 bsub。

### R2-02：唯一 Schema 的原则已统一，字段和最早样例交付还要统一

位置：[B01](../../../.omo/plans/acp2-parallel-plan-b-runtime.md#L180)、[A 证据协议](../../../.omo/plans/acp2-plan-a-cccp-science.md#L112)、[C T-06](../../../.omo/plans/acp2-plan-c-rph-workbench.md#L239)。优先级：高，在 B01 冻结前处理。

B 已明确接受 `scenario_id` 别名并归一化为 `scenario`，所以这项不再视为冲突。但 C 的“逐字段”清单仍未列 B 的 `candidate_revision`、`schema_dialect`、`evidence_kind`，平台标识主要放在 `platform{...}`；B 的共同字段又列出顶层 `job_id/attempt/release_id/submission_id/negotiated_protocol`。B 允许额外 `platform`，不等于已经定义如何填充共同字段或如何检查二者一致。

建议删去 A/C 重复定义的完整字段清单，改为引用 B01 的版本和摘要，只列扩展；如果保留清单，逐项同步。为独立 CCCP / fixture / live / aggregate 定义字段必填条件和 null 语义，平台标识选择一个规范位置。兼容别名只在入口归一化，规范输出只写一套。

样例交付也需要前移：B01 冻结要求 A/C 正负样例；A 最早明确的协议门在 A17，而 A17 又消费依赖 B01 的 B05。不要等到 A17 或完整 Harness 才给样例。建议 `B01 draft → A todo 4 / C T-02 提供轻量回执样例 → B01 freeze`，后续 Harness 再做 writer 输出与规范样例的等价测试。

新增验收：同一校验器读取真实 writer 的完整输出，缺 candidate_revision、错误字段位置、双份平台标识冲突、fixture 冒充 live 均按确定规则处理。

### R2-03：LSF 的等待窗口还没有与实际命令绑定

位置：[C 时间规则](../../../.omo/plans/acp2-plan-c-rph-workbench.md#L115)、[C T-19](../../../.omo/plans/acp2-plan-c-rph-workbench.md#L369)、[B11](../../../.omo/plans/acp2-parallel-plan-b-runtime.md#L280)。优先级：高，在真实 LSF 验收前处理。

C 新增“场景 timeout 至少覆盖最长队列等待”，但 T-19 仍固定 2400 秒，T-20 固定 3600 秒，资源表保留 24 小时队列上限。队列占用上限不必等于允许排队时间；目前缺少一个实际测试窗口的参数化定义。若将 24 小时直接当最长等待，这些命令按新规则会在执行前记 NOT_VERIFIED。

建议 B07 冻结每个 LSF fixture 的 `max_queue_wait_seconds`、`max_run_seconds`、`max_prepare_seconds`、`cleanup_seconds`，从它们推导总 timeout；C 命令消费同一值，不再手写相互独立的期限。申请能在测试窗口内启动的小作业队列。

状态分类写清：执行前无法取得队列窗口可 NOT_VERIFIED；已执行的断言失败不能改写；到期仍有队列/远端任务时保留 submission 引用并对账，不能只写 NOT_VERIFIED 就把活动作业遗留。

### R2-04：B11 的正常产物和主动取消应分配不同 TaskRef

位置：[B11](../../../.omo/plans/acp2-parallel-plan-b-runtime.md#L280)、[B13](../../../.omo/plans/acp2-parallel-plan-b-runtime.md#L300)。优先级：高，在 B11 实测前处理。

B13 已增加单独计费的控制竞争 fixture，但 B11 仍要求 singlepoint 同时完成 `bstop/bresume`、confirmed cancel 和终态后的科学产物拉取。快速任务仍可能在控制调用前自然结束；主动取消的任务也不保证产生正常完成所需的科学结果。

建议 fixture 注册表至少区分 `completed_science_run` 和 `control_cancel_run`：前者证明正常科学执行与工件读取，后者证明控制与停止。取消任务的验收允许没有完成科学结果，但必须有正确终态、停止确认和回执。最简单的是把 B11 的控制断言完全归入 B13，并在最终 LSF 矩阵关联这两个独立事实。不要让一个 TaskRef 同时满足 completed 和 cancelled 的期待。

### R2-05：DA 的 3h45m 应是计算截止点，而不是证据阶段的自动失败点

位置：[C T-35](../../../.omo/plans/acp2-plan-c-rph-workbench.md#L529)。优先级：中，在 H4 前处理。

新版修正了 result 枚举，但仍规定 T-34 耗时达到 3h45m 就把证据 phase 判 FAIL。此时距离 4 小时上限仍有 15 分钟；哪怕 TS/IRC 均已有效、只读导出只需一分钟，也会被提前判失败，与“保留有界证据导出时间”的新规则不一致。

建议预先划分科学运行预算与证据预算；科学运行接近截止点停止追加昂贵步骤，证据阶段使用预留窗口完成验证/导出。判断是否 FAIL 看必需操作是否完成及是否实际超限，不只看已用时间。科学正例不足时 H4 保持开放，但仍生成诚实的报告。

同样明确“达到”与“超过”：全部必需操作完成且使用量恰为允许上限时是否允许 PASS；负测中拒绝第 13 次调用本身应按预期拒绝验收，不能和场景真实超支混为一谈。

### R2-07：新增预算代理需要明确实现与 token 限制方法

位置：[C T-13](../../../.omo/plans/acp2-plan-c-rph-workbench.md#L309)。优先级：中，在真实模型调用前处理。

T-13 新增 `acp2_experience_budget_proxy.py`，是把前置预算落地的进步，但正文只写“启用”，没有明确实现、启动/就绪、停止、状态恢复和上游协议的步骤。当前验收主要证明拒绝第 13 次请求，不能覆盖单个请求耗尽 token 预算。

建议在同一 todo 内明确该脚本由 C 实现并自测：请求前预留额度，限制单次输出上限；流式与非流式都采集实际 usage；中断/上游错误后按明确规则结算，缺 usage 不伪造精确值；Web/headless 实际路由均经过代理。检查重启是否允许恢复预算，以及预算是场景级还是整个验收会话级。

请求次数、边界和错误路径可先用受控上游验证；真实 DSH/模型另做一次生产形态的贯通测试。无需为验证计数器额外消耗十二次真实模型请求。
