## 3. 需要优先处理的 4 项 P0

### P0-1 · B-T76 与最终验收存在闭环

**位置：** [B-T76](.omo/plans/acp-parallel-plan-2-services.md:918)、[Final verification wave](.omo/plans/acp-parallel-plan-2-services.md:928)、Success criteria 的 IS-1/IS-11。

T76 必须等 F1–F4 APPROVE 才执行；但 F-wave 前言仍要求在 **ALL todos** 后运行，F1 要核对每项 Acceptance 的执行证据，IS-11 又把 T76 发布记录列为 F4 的证明。因此按完整验收条件执行时，F-wave 要等 T76，T76 又要等 F-wave。只在 T76 写“序在终验之后”不足以消除 F1/F4 的反向要求。

**建议直接修改：**

1. F-wave 的入场范围改为“本次 release 范围内的发布前任务，不含 T76 及未进入范围的条件项”。
2. F1/F4 的检查清单显式排除实际发布结果；检查 T71 的发布准备、回退条件和预生产证据。
3. F1–F4 通过后执行 T76，再由发布后核对记录关闭发布结果。发布失败进入恢复与复验，不得倒签 F-wave。
4. IS-11 分“发布前验收”和“发布后结果”；IS-1 不再要求 F1 已看过尚不能执行的 T76。

**验收：** 画出的任务依赖是单向的 `发布准备 → 发布前终验 → T76 → 发布结果核对`；任何发布前门都不消费发布后的证据。这里不需要再增加一次用户确认来补偿计划自身的环。

### P0-2 · C-T25 已经消费 TMS 资产，切换点仍然太晚

**位置：** [C-T25](.omo/plans/acp-parallel-plan-3-cccp.md:464)、T26/T28/T30；源码 [models.py](src/acp/nmr/models.py:35)、[reference_validation.py](src/acp/nmr/reference_validation.py:673)。

目前计划把 `models.py` 和 TMS 查表在 T25 迁到 CCCP，同时明确本片不迁资产。实际 `_load_tms_table()` 按 `Path(__file__).parent / "models" / "tms_references.txt"` 读取；搬到新包后该目录不存在，`lookup_tms_shieldings()` 会返回 `(None, None)`。这发生在 T26 的模型/loader 切换之前，可能改变默认引用值和科学输出。

还有一个反方向窗口：T26 移走旧资产后，尚留在 ACP 的 `reference_validation.asset_hashes()` 仍按旧模块旁 `models/` 读取，要到 T28 才迁移；它会把原本存在的摘要记为 `None`。T30 的最终路径审计无法修复前序提交已经产生的退化。

**修改建议：** 将资源位置作为早期独立交付，安排在 T25 前，或把首次消费资产的相关修改组合成一个原子集成批：

- 建 CCCP 内唯一的资产定位入口，避免各模块继续用自身 `__file__` 推导资源位置。
- 单一资产位置、全部已有 reader、package-data 与打包测试同批切换。至少核对 models/TMS、error_model、fchl、reference_validation、dp5q_stub 的路径语义；保留 stub 本来就缺失的参数状态。
- 尚未迁移的 ACP reader 可以调用 CCCP 的定位入口；不复制第二份资产，不从 CCCP 反查旧 ACP。
- T30 仅审计最终状态，去掉可能让执行者误解为 T26 必须等 T30 才能提交的“同批收口”措辞。

**验收：** 冷启动进程在 T25 完成后即能取得相同 TMS 数值；每个已合入节点的资产摘要不由非空变成 None；源码和 wheel 均通过。测试必须清除进程内 TMS 缓存影响，不能让迁移前缓存掩盖路径缺失。

### P0-3 · 滚动打包写入了正文，前置依赖仍在完整 C08 之后

**位置：** [B-T40](.omo/plans/acp-parallel-plan-2-services.md:556)、[C-T39](.omo/plans/acp-parallel-plan-3-cccp.md:618)、C-T26/T30。

T26 要求同批取得 B 的 package-data/打包测试补丁并做 wheel 验证；但提供该滚动维护的 B-T40 仍依赖 B-T35–37、输入整个 C08。C-T39 又依赖 T30/T33/T38，而 T30 在 T26 之后。正文允许“滚动”，按现有任务调度却不能在 T26 前取得一个已满足前置条件的打包交付。

**修改建议：** 使用现有编号的子项即可，不必重写全路线：

| 子项 | 前置 | 交付 |
| --- | --- | --- |
| C39a 首批构建/资产变更规格 | C00 登记与本批科学变更规格 | 精确构建与 package-data 补丁、资产摘要、验证命令 |
| B40a 本批打包维护 | C39a 与对应迁移补丁就绪 | 与科学变更组成一个集成批的应用回执 |
| C26/T25 相关资源切换批 | 相应源码和 B40a 补丁齐备 | 同一提交集合的源码及安装包证据 |
| C39b/B40b 完整发行 | 声明范围内迁移完成 | 最终发行清单、文件归属与角色依赖证据 |
| C54 最终复验 | release 源码冻结、B 已应用选定补丁 | 对同一个候选 release 重建/安装/运行的证据 |

“补丁齐备”和“集成已应用”分开，不能要求 B 在科学源码尚未准备时先改 package-data，也不能要求 C 在 B 尚不允许开工时先完成安装验收。集成批只能在全部补丁具备后整体检查和合入。

**验收：** T25/T26 的测试不再等待完整 NMR、大数据、init 和完整 C08；完整发行仍有自己的最终门。C54 的证据不得早于本次 release 选定的插件、配置及其他源文件变更。

### P0-4 · T72 解决了过渡装配，尚未解决独立实现和 worker 装配

**位置：** [B-T72](.omo/plans/acp-parallel-plan-2-services.md:194)、T6/T11/T25、[B-T31](.omo/plans/acp-parallel-plan-2-services.md:464)、IS-3。

T72 对旧实现注入的规定是有效的迁移策略，但后续任务仍主要是委托和行为保真，没有列出全部被注入实现实际迁入 Services 的任务。IS-3 仍要求 Services 成为唯一实现驻点，Success criteria 却用只证明过渡注入的 T72 证明独立性。

尤其是 T31：worker 由 Envelope 在新进程或远端启动，却仍要求通过“旧 acp 装配”取得 step requirements。进程内函数/对象不会随 Envelope 自动到达远端；若远端启动再加载旧 ACP 实现，就没有满足独立 worker 的声明。

**修改建议：**

- 在 T72 形成可核对的 `旧实现 → 目标模块 → 实际迁移任务 → 移除注入任务 → 验收` 表，任务列必须是具体任务或子项，不能只有“后续迁移”。
- 新增或补齐 schema/store、控制与恢复、Data writer/cache、plan/step requirements 和参数转换所需的迁移闭包；允许按声明的工作流范围分批。
- 过渡 controller 可以由 ACP 装配；独立 worker 必须由 Services 自己的 composition root 从冻结数据构造依赖，且不连接 jobs DB。
- 独立性证据从 T72 移到实际移除旧实现后的任务；保留有明确定位的旧 CLI/import shim，不把 shim 所在命名空间与旧实现混为一谈。

**验收：** 在旧 ACP 实现不可用、无 Web 服务、无 jobs DB 连接的独立子进程中执行对应 Envelope。既要有成功 fixture 路径，也要有结构化失败与回执；不能靠父进程注入的旧对象通过测试。

## 4. 前端计划还应修改的内容

### P1-1 · T29 拆分测试后，T30 必须运行新的完整测试集合

**位置：** [A-T29](.omo/plans/acp-parallel-plan-1-frontend.md:430)、T30、Verification strategy。

T29 已增加旧→新 node ID 与 fixture 映射，这是有效改进。但 T30 和验证策略仍要求“前端四 pytest”，命令固定旧的四个测试文件。新拆出来的测试文件不一定会被这些命令收集，可能出现拆分前的用例全部保留、最终回归却只跑残留旧文件的问题。

**改法：** T29 同时更新一个权威的前端测试选择清单或 marker，T30/CI/浏览器配套步骤统一引用；扩展 API 回归继续按职责列出。记录拆分前完整 node ID 集合与拆分后映射，证明最终命令实际收集这些用例，而不只证明全仓 collect-only 能找到它们。

**验收：** 在一个新拆分测试中注入必然失败的断言，仅在临时副本执行 T30 的真实选择命令，必须失败；移除负例后恢复。这比只比较用例总数更能证明最终门没有漏收。

### P1-2 · A04/A06 条件任务需要明确的激活规则

**位置：** [A 条件任务表](.omo/plans/acp-parallel-plan-1-frontend.md:67)、Must NOT、T34/Success criteria。

条件表已经列出 owner、交付物和退出条件，但 Must NOT 仍无条件禁止实现 A04/A06；表也没有编号、Blocked by 和交付证据任务，34 项全关闭仍不包含其实现。执行者可能据其中一处启动新能力，据另一处判定越界。

**改法：** 明确两个阶段：“A00–A03/A05 实施时不启用新能力；已登记的条件任务在对应版本交付物通过入场检查后纳入本次范围”。为需要在当前里程碑启用的条件项分配任务或子项，写明输入版本、消费测试、B 侧接收项和退出门。无需现在实现未冻结的字段。

区分 S0 收口的 F1 与接入新服务后的 F1：可以用明确的前端构建摘要或如 `F1-base/F1-integrated` 的测试记录名称，避免同一个 F1 指代两份代码而混用 S0 证据。新代码仍需能力缺失时的 S0 回退验证。

**验收：** B-T75 能引用一个已产出实际前端代码和消费测试的任务；若本次不启用 A04，记录明确未接入，不能关闭相关产品/UI 目标。

### P2-1 · T1 的 worktree 与环境命令应能在新环境直接执行

**位置：** [A-T1](.omo/plans/acp-parallel-plan-1-frontend.md:150)。

计划支持独立 worktree，但又直接引用 `.git/refs/heads/main`；linked worktree 的 `.git` 通常是文件，直接读取该路径不成立，main 也可能在并行期间推进。改为冻结基线提交及文件摘要，并通过 Git 命令解析引用；记录任务分支，不要求它始终等于实时 main。

新建 venv 后只安装 `.[browser]` 也不保证 pytest、API 和 HTTP 测试依赖齐全。补一条按本路测试范围安装依赖的可复现步骤，沿用项目 extras 约定，再安装浏览器依赖；所有命令都使用已记录的本路解释器。这里属于完善执行说明，不构成新的产品功能。

## 5. Services 计划的进一步建议

### P1-3 · 首批里程碑与完整发行仍被同一个任务状态绑在一起

**位置：** B-T34/T40/T41/T74、C-T10/T39/T44/T46，各自依赖矩阵与最终验收规则。

已写“首批与完整退出门分开”，但 B-T34 Acceptance 仍要 15 active 全覆盖，B-T41 仍等待 T32–T34 和完整 T40；C-T44 的 M1 插件还等 C-T39，而 C39 等完整 NMR/大数据。C-T10 虽按工作流交付，任务头仍等 T8/T9，simple 已满足时也不能按硬表立即交付。

另一个次序问题：完整 CLI 的唯一证明方 T74 依赖 T41，而 T41 的配方包含“首个本地科研闭环已复现”。这让配方验收先于本应证明完整 CLI 的实际实现。

**改法：** 将重复执行和分阶段完成显式建模，而非给同一个二元 checkbox 写两个门：

为 M1/M2/M3 分别列所选任务/子项、必需证据和已延期能力。最终门只检查本次声明范围，条件项不适用仍保留后续工作，不能为了 ALL todos 自动进入收费/Hosted。

**验收：** M1 的依赖闭包不包含未选 NMR、完整 15 项覆盖、价格审批和后置组件 PoC；它仍包含所承诺的真实 CLI、GUI/init 和插件样板。

### P1-4 · T69/T75 的验收责任和顺序需要统一

**验收：** 每个组合有唯一执行任务和提交摘要，最终报告在组合结果之后生成，旧的禁止执行表述消除。

### P1-6 · T14 必须定义缺少预期摘要的历史工件如何接纳

**位置：** B-T11/T14/T16、源码 [Product](src/acp/storage/manifest.py:41)。

T14 新要求摘要来自冻结的源 manifest/完成回执，这比下载后自算更有依据。但现有 v2 Product 的基本字段是 id/label/path/kind，metadata 可选，并不保证有内容摘要；历史任务也不一定有新回执。科学 step_result 能覆盖一部分文件，不能默认覆盖 catalog、全部产品及历史任务。

**改法：** 定义新工件的验证记录与历史接纳协议。新 worker 发布需要的摘要可以放兼容 metadata 或 Data 自己的版本化清单，保持旧 v2 reader 兼容。历史工件优先利用有效既有摘要；没有摘要时，先通过受控源端快照/校验流程取得并登记基线，标明接纳来源和验证级别。不能靠“下载完算一个 hash”伪称已有预期摘要，也不能让所有旧任务永久 pending。

mutable 的日志、候选与组织文件另以 revision/generation/range 协议定义读取一致性，不能统一当作一次 attempt 下永不变化的完成工件。

**验收：** 新回执结果、带摘要的旧结果、无摘要的旧 v2/历史结果、mutable 资源和损坏源各有用例；冻结 F0 仍能读取原有合法任务。

### P1-7 · outbox 必须进入现有 CAS 的同一个连接，故障预期也要修正

**位置：** [B-T23](.omo/plans/acp-parallel-plan-2-services.md:380)、源码 [JobStore.transition](src/acp/scheduler/store.py:194)。

事务 outbox 的方案已补齐。但当前 `transition()` 在自身连接中更新、`conn.commit()` 后返回；外层再插入 outbox 仍然是两个事务。T23 应明确扩展 owner repository 的事务边界，不能只在 Runtime facade 外包一层调用。

T23 的 QA 又要求“CAS 与 outbox 之间崩溃→重启补齐事件”。如果两者同事务且尚未提交，正确结果应该是状态与 outbox 一起回滚；不能为未提交状态补事件。

| 故障点 | 应断言的结果 |
| --- | --- |
| CAS 守卫失败 | 状态不变，无对应 outbox 事件 |
| UPDATE 后、outbox INSERT 前或事务提交前崩溃 | 二者一起回滚，无未提交事件 |
| 同事务提交后、投递前崩溃 | 状态与 outbox 均存在，重启补投 |
| 投递成功、确认前崩溃 | 可重放、按稳定 ID 去重，不重复改变状态 |

还应验证旧 after_seq/JSONL 兼容出口在投递重试时如何去重；只有消费端忽略重复并不证明兼容文件不会反复追加同一事实。

### P1-8 · availability 与 freshness 要有不同的语义

**位置：** [B-T20](.omo/plans/acp-parallel-plan-2-services.md:350)、B-T15/T22、A 条件任务表。

T20 一方面新增 freshness，另一方面又用 `availability=stale/absent` 表达缺投影，并用 observed_at 与 revision 更新时间比较作为单调性断言。资源可读取性、投影是否跟上权威状态、科学结果是否完整是不同维度；它们共用模糊枚举会使 A 的 prepare 和刷新策略产生分歧。

**改法：** B-T3 冻结字段定义：资源是否已准备由 availability 表达，投影是否过期由 freshness 及其依据 revision 表达；科学 partial/failed/unavailable 继续按 C 产品契约保留。observed_at 用于诊断，不作为跨进程/跨节点的严格新旧判定。

投影记录其 `basis_revision`，以 job/attempt 和对应 owner revision 比较。新状态已提交但投影尚未跟上时，jobs 基础事实仍可显示，旧投影明确 stale。不同 owner 的 revision 不相互替代。

**验收：** 覆盖“资源 ready 但投影 stale”“无投影但 jobs 事实可见”“旧 attempt 投影迟到”“时钟偏移但 revision 正确”等组合，A 使用同一组 fixture 判断是否 prepare、刷新或显示部分数据。

## 6. CCCP 与跨路产品交接还应补齐的内容

### P1-9 · 产品描述和交接要求需要落到实际生产与 adapter 任务

**位置：** C-T11–T14、C-T32/T33、B-T28/T46、A 科学产品条件任务。

C-T11/T12 已要求定义生成函数和时机，但 Acceptance 仍主要检查 schema、fixture 和 round-trip；T13 要“指明 B 接收任务”，B 现有任务却没有明确接管新科学产品→frames/annotation 的完整 adapter。B-T46 的溯源投影不能自然代替该 adapter。

**改法：** 为本次声明支持的每类产品建立一行实装闭包：

`真实生成入口 → C 产品 writer/reader → B Data 登记/读取 → B frames/annotation adapter → A 消费与选择映射 → 验收任务`。

在 C 的对应迁移任务中完成真实生成入口接线，B 增加明确任务或 T28 子项实施 adapter，A 的条件任务引用该产物版本。旧结果使用兼容 reader/转换，不复制科学算法；新结果不得只有示例 JSON 而没有生产调用链。

**验收：** 同一固定输入由生产入口产生数据，经 B 发布和投影后被 A/Python 消费；单位、atom_uid、frame/point/native mode、缺失原因和块索引逐项一致。仅 schema 测试通过不能关闭此项。

### P1-10 · C-T13/T39/T42 的关键交接物不能等最终总结才入仓

**位置：** [C-T13](.omo/plans/acp-parallel-plan-3-cccp.md:332)、T39/T42、T51、共同证据规则。

C-T10/T33/T51 的 tracked 修改已生效，但 T13 仍写 `Commit: N（handoff 在 .omo；如需入库由 B 决定）`，与共同规则冲突。T39/T42 的精确打包/节点请求也未明确受控交付路径。A/B 在独立 worktree 消费这些材料时不能等待整路完成后的 T51 汇总。

**改法：** 将契约样例、字段映射、构建配置、节点依赖请求及期望输出按产生时点交付到登记的 tracked 路径，明确唯一写者和提交回执；原始大日志继续外置。B 集成共享文件不意味着 C 无须交付受控输入。T51 只汇总和审计已交付材料。

**验收：** 在另一份干净 worktree/clone 中，仅凭登记的提交和稳定工件位置即可取得交接物并复现消费测试，不依赖提供者本机 `.omo`。

## 7. 建议的最小修改批次

本轮无需再扩大计划规模，优先完成以下三批修订：

1. **修正执行门与任务状态**：消除 T76/F-wave 环；把首批/完整任务拆成明确子项；统一 Depends on、Blocks 与波次，修 T3 台账格式。
2. **补齐真正的实施闭包**：NMR 首次资源依赖前移；滚动打包早期子项；Services 移除旧实现的任务；worker 自足装配；科学产品生产与 B adapter 接线。
3. **修正验证与交接入口**：拆测试后的完整命令、正确 outbox 故障断言、旧摘要接纳、availability/freshness 样例、四组合报告顺序和 tracked 早期交付。

每批修改只需要同步任务正文、依赖、验收和产物这四处；不要再仅在全局约束追加一句“按评审执行”。完成后可按受影响子图核对，避免反复全量改写已经稳定的前端 API、身份和科学数值规则。
