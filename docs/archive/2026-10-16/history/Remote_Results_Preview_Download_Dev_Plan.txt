

  
ACP 远程结果预览与下载开发文档

  

    目标：让网页用户在不把远程计算节点数据同步到 web 服务器的情况下，直接预览和下载结果。

1. 需求确认

  
通过五轮问题确认，最终需求如下：

  
    
      
 | 维度 | 选择 | 说明

    
    
      

         | 数据位置
         | 远程计算节点原始文件
         | log、out、xyz、chk、rwf、cube 等保留在远程节点，不预先拉取到 ACP_runs/。
      

      

         | 预览范围
         | 全部
         | 文本/日志、三维结构、能量图/反应路径、NMR 谱图/报告、波函数/cube。
      

      

         | 下载策略
         | 单文件下载 + 打包下载
         | 每个文件可单独下载；同时支持把整个任务目录打成 ZIP 流式下载。
      

      

         | 缓存
         | 完全禁止
         | 不在服务器磁盘、内存池、SQLite 或数据库中持久化任何结果数据。
      

      

         | 大文件
         | tail + range 分页
         | 大文件不走全量文本预览，而是按行尾或字节范围分段读取。
      

      

         | 打包格式
         | ZIP
         | 最通用，用户双击即可解压。
      

      

         | cube 预览
         | 仅下载
         | 轻量服务器不做等值面/切片渲染；cube 文件通过下载查看。
      

      

         | 前端版本
         | ACP Workbench v2
         | 复用现有 3Dmol 查看器、文件树、节点面板。
      

    
  

  
2. 设计原则

  
    
数据零落地：原始文件始终只在远程节点；web 服务器仅做 SFTP 代理。
    
请求级流式：每个 HTTP 请求触发一次 SFTP 连接；读取、打包、返回后立刻释放连接。
    
无持久化缓存：不写入服务器磁盘，也不在数据库/缓存中保留结果。
    
大文件受限：超过阈值的文本文件仅支持 tail/range；打包下载总量受上限约束。
    
轻量优先：避免在服务器做重型计算（如 cube 渲染、大文件全量解析）。
  

  
3. 后端设计

  
3.1 现有能力

  
代码库已具备远程文件按需拉取能力：

  
    
src/acp/scheduler/remote/fetcher.py：SFTP 连接池、list_files、read_file、stream_file、log_tail。
    
src/acp/api/v1_routes.py：
      /api/v1/jobs/{id}/remote-files（列表）
      和
      /api/v1/jobs/{id}/remote-files/{path}（单文件下载）。
    
  

  
3.2 需要增强的 Fetcher 方法

  
在 RemoteResultFetcher 中新增以下方法：

  def read_range(record, filename, offset, limit) -> bytes
    """按字节范围读取远程文件。"""

def read_tail(record, filename, lines) -> str
    """通用 tail：读取任意日志文件最后 N 行。"""

def file_stat(record, filename) -> dict
    """返回 size / mtime，用于前端判断预览策略。"""

  
3.3 API 端点

  
    
      
 | 方法 | 端点 | 状态 | 说明

    
    
      

         | GET
         | /api/v1/jobs/{id}/remote-files
         | 已存在
         | 列出远程任务目录顶层文件。
      

      

         | GET
         | /api/v1/jobs/{id}/remote-files/{path}
         | 已存在
         | 单文件流式下载。需根据扩展名补正确 Content-Type。
      

      

         | GET
         | /api/v1/jobs/{id}/remote-files/{path}/preview
         | 新增
         | 文件预览，按 mode 参数分发。
      

      

         | POST
         | /api/v1/jobs/{id}/remote-files/download
         | 新增
         | 把整个任务目录打成 ZIP 流式返回。
      

    
  

  
3.4 预览端点 /preview 参数

  
    
      
 | mode | 参数 | 返回 | 适用文件

    
    
      

         | text
         | 无
         | UTF-8 文本
         | .log, .out, .gjf, .com, .txt, .json, .csv
      

      

         | tail
         | lines=500
         | 最后 N 行文本
         | .log, .out
      

      

         | range
         | offset, limit
         | 字节范围内容
         | .log, .out, .txt
      

      

         | structure
         | 无
         | xyz / sdf 文本
         | .xyz, .sdf, .mol
      

      

         | report
         | 无
         | 结构化 JSON
         | NMR 报告、能量排序文件
      

    
  

  
3.5 打包下载端点

  
实现要点：

  
    
使用 zipfile + io.BytesIO 在内存中分块生成。
    
通过 StreamingResponse 返回，不在磁盘生成临时文件。
    
遍历远程目录时，用 FileStager.list_remote_dir 递归获取文件列表。
    
逐个文件流式写入 ZIP 条目，避免单文件占用大量内存。
    
返回头：Content-Disposition: attachment; filename="{job_id}.zip"。
  
  POST /api/v1/jobs/{id}/remote-files/download

# 返回
Content-Type: application/zip
Content-Disposition: attachment; filename="{job_id}.zip"
<流式二进制数据>

  
3.6 解析器层（无缓存）

  
复用现有解析器，在请求时实时解析：

  
    
NMR：acp/nmr/parser.py → acp/nmr/calibration.py → acp/reports/nmr_report.py。
    
能量/构象：从 result.state、all_conformers.xyz 或相关能量文件实时解析。
  
  
所有解析器输入为文件内容或流，输出为 JSON；不写入任何缓存。

5. 安全与限制

  
    
      
 | 项 | 策略

    
    
      

         | 路径穿越
         | 复用 fetcher.py 中的 _safe_join，确保文件路径不逃逸远程任务目录。
      

      

         | 预览文件类型
         | 白名单：.log, .out, .xyz, .sdf, .mol, .gjf, .com, .json, .csv, .txt。禁止 .chk/.rwf 直接文本预览。
      

      

         | 文本预览大小
         | ≤ 50MB；超过返回 413 Payload Too Large 或自动降级为 tail。
      

      

         | 打包下载大小
         | ≤ 5GB（可配置）；超过返回 413 并提示分批下载。
      

      

         | SFTP 超时
         | 所有远程操作加超时，避免挂死连接。
      

      

         | 认证
         | 当前版本为可信内网部署，不新增认证；若未来暴露公网，需前置反向代理 + IP 白名单。

8. 风险与对策

  
    
      
 | 风险 | 影响 | 对策

    
    
      

         | 远程节点不可达
         | 用户无法预览/下载任何结果
         | 这是“数据不落地”的固有限制；前端给出清晰错误提示。
      

      

         | 打包超大目录
         | 流式 ZIP 生成慢、超时、内存高
         | 设置 5GB 上限；超限时拒绝并建议分批下载。
      

      

         | 重复解析
         | NMR/能量报告每次请求都重新解析远程文件
         | 在请求级内存中缓存解析结果；请求结束后释放（符合不持久化缓存要求）。
      

      

         | SFTP 连接池耗尽
         | 大量并发下载导致连接不足
         | 复用现有连接池；监控并发数；必要时加队列/限流。
      

      

         | cube 无法预览
         | 波函数可视化缺失
         | 第一阶段仅提供下载；后续若需要可讨论客户端渲染或专用查看工具。
      

    
  

  
9. 审查意见与改进建议

  
基于对现有代码库（src/acp/scheduler/remote/fetcher.py、src/acp/api/v1_routes.py 等）的核查，本文档存在以下需要修正或补充的问题。

  
9.1 缓存策略自相矛盾

  

    问题：需求确认中“缓存：完全禁止”，设计原则第 3 条重申“无持久化缓存”，但在第 8 节“风险与对策”中却提出“在请求级内存中缓存解析结果”。这会让实现者困惑：到底能不能缓存？
  

  
    
建议把“缓存”拆成两个概念：持久化缓存（禁止）与请求级临时缓存（允许）。
    
为请求级缓存给出明确边界：最大内存占用、TTL、请求结束后必须释放。
    
例如：NMR 报告解析结果可在一次 GET 请求内缓存 5 分钟，但禁止写入磁盘、SQLite 或 Redis。
  

  
9.2 打包下载端点设计不当

  

    问题：第 3.3 节使用 POST /remote-files/download 下载一个资源，且该路径与 /remote-files/{path} 存在冲突风险。
  

  
    
REST 语义下，获取资源应使用 GET。POST 适用于创建或触发异步任务。
    
路径冲突：如果 {path} 使用 path converter，理论上 FastAPI 会优先匹配静态路由，但文档应明确说明路由注册顺序。
    
建议改为 GET /api/v1/jobs/{id}/remote-files/archive 或 GET /api/v1/jobs/{id}/remote-files?archive=zip，语义更清晰。
  

  
9.3 “流式 ZIP”实现描述不准确

  

    问题：第 3.5 节说“使用 zipfile + io.BytesIO 在内存中分块生成”，但 BytesIO 会把整个 ZIP 缓冲在内存。若按 5GB 上限执行，内存会爆炸。
  

  
    
Python 标准库 zipfile 不支持边写边丢的流式生成。
    
若要求真正流式，需要引入第三方库如 zipstream-ng、stream-zip 或自行实现 chunked ZIP 生成。
    
如果仍用 BytesIO，必须大幅降低上限（例如 200MB），并在文档中明确说明这是“内存缓冲”而非“流式”。
    
建议补充：在打包前先用 file_stat 统计总大小，超过阈值直接拒绝，避免读到一半才 OOM。
  

  
9.4 认证与授权缺失

  

    问题：第 5 节“认证”仅写“可信内网部署，不新增认证”。这不足以防止用户 A 访问用户 B 的 job。
  

  
    
即使内网，也应复用现有的 job 归属或 project 权限模型。
    
建议 _get_remote_job_record 中增加调用者校验，确保用户只能访问自己/所属项目的 job。
    
至少记录访问日志，便于事后审计。
  

  
9.5 路由顺序与模式冲突

  

    问题：第 3.3 节的端点列表没有说明 FastAPI 路由注册顺序。
  

  
    
/remote-files/{path:path} 会匹配任何路径，必须在 /remote-files/{path}/preview、/remote-files/download 之后注册，否则静态路由会被“吞掉”。
    
建议把 /preview 改为独立前缀如 /remote-files/{path:path}/preview，并确保在 /{path:path} 之前注册。
  

  
9.6 预览模式不完整

  

    问题：第 3.4 节的预览模式缺少错误降级和参数约束。
  

  
    
tail 模式应限制最大行数（如 5000），避免拉取全部日志。
    
range 模式应说明 offset 是否支持负数、是否支持 HTTP Range 标头。
    
report 模式应给出 JSON Schema 示例，便于前端对接。
    
建议在文件大小超过阈值时自动降级为 tail，而不是返回 413 让前端重试。
  

  
9.7 大文件预览阈值缺乏依据

  

    问题：50MB 文本预览在 SFTP 高延迟网络下仍可能很慢，且阈值未与现有常量对齐。
  

  
    
fetcher.py 已定义 _MAX_READ_BYTES = 200 MB，建议把 50MB 预览上限作为配置项，并说明其小于 200MB 的读取上限。
    
建议区分“读取上限”和“在线预览上限”，避免用户误以为 50MB 以上不能下载。
  

  
9.8 错误码与状态约定不足

  

    问题：文档只提到 413，缺少统一的错误码表。
  

  
    
 | HTTP 状态码 | 触发场景

    
      
 | 400 | 参数错误、文件类型不在白名单

      
 | 403 | 无权访问该 job

      
 | 404 | job 或文件不存在

      
 | 413 | 文件或打包总量超过上限

      
 | 502 | 远程节点无法连接

      
 | 504 | SFTP 操作超时

    
  

  
9.9 缺少数据完整性校验

  

    问题：打包下载没有说明如何保证 ZIP 不损坏或不被截断。
  

  
    
建议单文件下载时返回 Content-Length 或 SHA-256 校验和。
    
打包下载完成后，可在响应尾追加一个 checksum 文件，或提供单独的 /remote-files/{path}/checksum 端点。
  

  
9.10 SFTP 连接与并发限制不明确

  

    问题：文档提到“复用现有连接池”，但没有给出具体配置。
  

  
    
建议明确：最大并发 SFTP 会话数、下载队列长度、连接超时时间、读取超时时间。
    
对于“下载全部”这类可能长时间占用的操作，应加全局锁或限流，避免拖垮远程节点。
  

  
9.11 cube 预览不是“风险”

  

    建议：第 8 节把“cube 无法预览”列为风险，但第 1 节已明确选择“仅下载”。这是设计决策，不是意外风险，应移到第 5 节“限制”或第 2 节“设计原则”中。
  

  
9.12 缺少技术依赖说明

  

    建议：若采用真正的流式 ZIP，需要引入新依赖。文档应列出候选库并比较优缺点，例如 zipstream-ng、stream-zip、zipfly。
  

  
9.13 实施阶段与前端不同步

  

    建议：Phase 4 前端文件树依赖 Phase 2 API 完成，但 Phase 5 报告解析又依赖 Phase 4 UI。建议把 API 和前端拆成可独立交付的迭代，而不是完全串行。
  

  
9.14 测试计划缺少性能基准

  

    建议：补充具体性能指标，例如：
    
      
1GB 日志 tail 100 行应在 3 秒内完成；
      
500MB 目录打包应在 2 分钟内完成且内存占用不超过 256MB；
      
100 并发文件列表请求不应导致连接池耗尽。
    
  

  
9.15 现有代码接口建议

  

    建议：结合现有 RemoteResultFetcher 实现，新增方法时与现有常量对齐：
    
      
read_tail 与现有 log_tail 统一：建议把 log_tail 泛化为任意文件 tail，或保留 log_tail 并新增 read_tail。
      
file_stat 返回结构可直接复用 RemoteFileInfo。
      
read_range 应考虑 SFTP 会话内的 seek 性能，必要时改为异步后台任务。

10.1 缓存策略：明确区分两类缓存

  
修复动作：

“禁止持久化缓存：原始结果文件不写入服务器磁盘、SQLite、Redis 或任何数据库。请求级临时缓存仅在单次 HTTP 请求生命周期内使用，请求结束后立即释放。”

10.3 流式 ZIP：引入真正的流式库

  
推荐方案：使用 zipstream-ng 或 stream-zip。

  # pyproject.toml
[project.optional-dependencies]
api = [
    "fastapi",
    "uvicorn",
    "zipstream-ng >= 2.0.0",  # 或 stream-zip
]

# v1_routes.py
from zipstream import ZipStream

@router.get("/jobs/{job_id}/remote-files/archive")
def download_remote_archive(...):
    def files_iter():
        fetcher = _remote_fetcher(request)
        for finfo in fetcher.list_files(record):
            yield finfo.name, fetcher.stream_file(record, finfo.name)

    zs = ZipStream(files_iter())
    return StreamingResponse(
        zs,
        media_type="application/zip",
        headers={"Content-Disposition": f'attachment; filename="{job_id}.zip"'},
    )

  
    
在打包前，先递归计算总大小，超过 5GB 直接返回 413。
    
如果无法引入新库，改为内存缓冲方案：上限必须降到 200MB（与 _MAX_READ_BYTES 对齐），并明确在文档中说明。

def remote_file_checksum(job_id: str, file_path: str, request: Request) -> dict:
    fetcher = _remote_fetcher(request)
    record = _get_remote_job_record(job_id, request)
