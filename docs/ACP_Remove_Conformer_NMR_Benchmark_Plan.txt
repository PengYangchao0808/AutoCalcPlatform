C0 · 前置调研（v3 已关闭 —— 结论如下，无需再调研）

  实际逐行核对结果（ensemble.py:414-430 / energy.py:836-857）：下游只消费 2 个属性。
  
两个工作流调用 CRESTInterface.run_conformer_search() 后，只读取 crest_result.success 与 crest_result.error_message；ensemble XYZ 路径由调用方自行拼接（crest_dir / "crest_conformers.xyz"，含 glob 回退），不从 result 对象读取任何文件路径或能量数据。计划 v2 假设的 .xyz_file / .energies / .conformer_energies / .output_dir 等属性访问均不存在。

  属性映射表（即为 C2 接线标准）：
  
    
 | 旧用法 | 新接口获取方式（CrestBackend.search 契约）

    
 | crest_result.success（失败时 raise RuntimeError） | search() 失败时直接抛异常（携带 stderr/错误信息），成功才返回——调用方删掉 if 判断

    
 | crest_result.error_message | 并入异常 message

    
 | crest_dir / "crest_conformers.xyz"（调用方自拼 + glob 回退） | 保持调用方自拼逻辑不变；search() 只需接收 output_dir/output_name 并保证产物落盘。可选增强：返回产物 Path 替代 glob 回退

  
  
结论：CrestBackend.search() 契约极简——输入 coordinates/symbols/output_dir/output_name/charge/multiplicity/energy_window，失败抛异常，成功返回 None 或产物 Path。v2 标注的"Part C 最大风险"实际为低风险机械改造。

  
【v5 重要发现】CrestBackend.search() 已经实现（acp/backends/crest.py:123-143）：签名 search(initial_xyz: Path, charge, multiplicity, output_dir, **kwargs) -> Path，失败 raise RuntimeError、成功返回产物 Path——与 C0 契约完全一致。当前零调用方（ensemble/energy 仍绕过 backend 直连 CRESTInterface）。故 Part C2 无需"设计/新增 search()"，仅做接线：让 ensemble.py/energy.py 调用既有 require_backend("crest").search(...)。可选增强：把 ensemble.py:430 的 glob 回退替换为 search() 返回值。
