**1. 高优先级：C-T54 的发布前后定位相互矛盾**

证据：[C-T54](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-3-cccp.md:788) 要求 B 应用构建补丁、候选源码冻结后，对合并版本重新构建和安装，并明确 `Blocks: B release`。但 [最终验收说明](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-3-cccp.md:824) 将它排除在 F1–F4 前置之外，认定为发布结果核对；[IS-10](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-3-cccp.md:854) 也写成发布后证据。

影响：按任务头执行，发布必须等待 T54；按终验说明执行，候选包尚未安装验证就可能通过发布前终验。C-T51 又等待“全部”任务，若其完整交接结果被 B 收口流程消费，还会产生发布前后相互等待的解释。

建议同时修改 T54、Final verification wave、IS-10 和 T51 的前置说明：

- 明确“B 应用回执”是补丁进入集成候选提交的回执，不代表生产发布。
- T54 定位为“候选版本发布前安装复验”，在声明范围内的源码与构建输入冻结、B 应用回执齐备后执行。失败则修复候选并重新验证。
- 发布前终验必须消费 T54 的结果；C-T51 在本次范围证据齐备后汇总，不能提前关闭仍等待跨路应用的项目。
- 实际发布与部署后冒烟继续由 B-T76/F5 负责。保留 B 已有的发布前 F1–F4 与发布后 F5 分离。
- M1 的安装验收按声明范围执行；未纳入的 NMR 等运行能力不能成为首批阻塞条件。随包资产的完整性按实际发行清单验收。

建议依赖顺序：

```text
B 应用补丁到集成候选 → 冻结源码/构建输入
→ C-T54 验证合并版本安装产物 → 本次范围证据汇总与发布前终验
→ B-T76 发布 → B-F5 核对发布结果
```

退出证据应关联候选提交、构建配置、安装产物摘要和运行环境；发布使用的产物须与所验产物可核对。影响产物的后续修改使原验收失效。此项必须在发布前收口，不阻止前序开发。

**2. 高优先级：B-T32 尚未等待独立装配，T77 的退出条件又提前消费了 T78 的能力**

证据：[B-T32](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-2-services.md:494) 仅等待 T30–T31 与对应 C01 闭包；[B-T78](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-2-services.md:521) 才负责从冻结数据启动独立 worker，却只列为终验与发布的前置。按任务头明确的本路数字依赖计算，T32 的前置闭包为 `{1, 2, 3, 30, 31, 72}`，没有 T77/T78。

影响：实际 runner/script_gen 可以在旧实现迁移和独立启动验证尚未完成时切换。T32 要求的独立入口验收也会提前消费 T78 的产物。

本轮补充核对：[T77](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-2-services.md:460) 已要求独立子进程执行 Envelope 成功与失败路径，而 T78 又依赖 T77。虽然任务头没有这条反向边，但若将 T77 的全部验收当成 T78 的入场条件，会要求在装配入口尚未实现时先证明它可用。

建议把职责和退出条件明确为：

| 任务 | 交付与退出条件 | 前置 |
| --- | --- | --- |
| T31 | worker/controller 协议与执行核心；可用受控依赖测试 receipt/CAS 边界 | 保留现有前置 |
| T77 | 声明范围内的实际实现迁入 Services、旧路径转发、移除旧实现注入；证明模块隔离与迁移行为等价 | 保留现有迁移前置；不要求尚未交付的 T78 全链路启动证据 |
| T78 | 新进程仅凭冻结 Envelope、StorageBinding 和工件完成装配；成功及结构化失败回执均验证 | T31、T77 |
| T32 的启用子项 | 本地/远端完整切换，旧 attempt 保持原协议，无双派发 | T78 + 对应工作流 C-T10a/滚动闭包交付 |
| T33/T34a | 执行完整性复核与所选工作流启用 | 消费上述切换和相应完整性证据 |

脚本、转换器等开发可以提前；实际启用必须等待独立启动证据。若保留 T77 中的端到端说明，应写成“由 T78 统一证明”，不能同时要求其在 T78 开始前通过。

另外，将 T77 的“无 jobs DB 连接”限定于 worker 独立性探针。controller/store 的持久化、CAS、恢复测试应使用隔离数据库，不能将整个 Services 的验收都套用 worker 禁 DB 条件。

此项必须在首次切换新执行入口前收口。

**3. 中优先级：B 计划仍未实际接收科学产品 adapter 的实现责任**

证据：[C-T13](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-3-cccp.md:335) 要求 B 提供产品到 frames/annotation 的适配；[A-GT3](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-1-frontend.md:74) 等待这个 adapter。当前 [B-T28](/ACPServer/AutoCalcPlatform/.omo/plans/acp-parallel-plan-2-services.md:439) 只收敛已有工件发布、markers 和 manifest。B-T3 负责契约样例；B-T46 负责研究溯源边投影，两者也没有承担科学产品到帧视图的实现。

影响：C 可以交付 schema，A 可以准备消费者，但中间没有明确任务负责将实际产品接到现行视图契约。后续交接表填写任务号，无法替代接收任务本身的范围、前置和验收。

建议将 B-T28 拆成两个可独立判定的子项：

| 子项 | 实现范围 | 依赖与验收 |
| --- | --- | --- |
| B-T28a | 既有 Data 发布、markers、manifest 入口收敛 | 保留原有行为及时序，不等待全部新科学产品 |
| B-T28b | 本次支持产品的 Data 登记/读取、frames/annotation adapter、必要的历史结果兼容接线 | 消费 C-T13 契约/fixture 与对应生产入口；通过 `TrajectoryFrame.to_node()` / `TrajectoryAnnotation.to_annotation()` 输出；由 A-GT3/B-T75 消费 |

按产品分别记录生成入口、reader/writer、Data 发布、视图映射和前端消费者。用同一固定输入贯穿验证单位、atom_uid、frame/point/native mode、缺失原因以及正常/空/部分/损坏/旧版本行为；科学算法继续由 C 唯一实现。

交接状态也需分开：C-T13 的“契约和映射可消费”允许 B 开始 adapter；C-T13 的“跨路端到端验收完成”则等待 B/A 接入后成立。不要让 B 等待 C-T13 全部验收完成，再由 C-T13 反过来等待 B/A。

这项应在科学产品集成任务排期时补齐，最迟在 A-GT3 激活前完成定义；不会阻断 A 的 S0 重构或已有结果发布。
