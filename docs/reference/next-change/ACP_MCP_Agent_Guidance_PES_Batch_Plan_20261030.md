日期：2026-10-30。核查 HEAD：`85834320`；工作区已有本次讨论对 perspective 的修改，未作为源码交付或验收结果。
状态：**设计与实施计划，尚未实施**。本文落实已确认的产品方向，不授权本轮启动真实模型/QC/LSF、修改生产服务或关闭发布门。

上位方向：[RPH / ACP perspective](<../../RPH_Agent_Three_Phase_Roadmap_20261027(1).md>)。本计划统一包含 MCP 基础易用性优化、按需科研指导、全自动初猜选择与 BatchOptimize 闭环，作为近期 MCP 工作的具体实施依据；其中“首版人工确认、以后才允许自动确认”的旧建议由本文取代。

## 1. 已确认的产品决定

1. **优先已有 harness 的用户。** 用户连接 ACP MCP 即可发现、学习和使用平台；不要求先安装 RPH，不另建 Agent 调度器。MCP 自身应做到可发现、可纠错、可取回、可续接；skill 不能成为弥补缺失 schema、错误信息或产物引用的唯一途径。
2. **复合工作流首批交付。** Confsearch、BatchOptimize、PESsearch、scan 一起覆盖。singlepoint、xtb_optimize、optimize、frequency 等作为必要的基础操作、补算与验证支撑。
3. **键长势能面扫描默认推荐 PESsearch。** 除体系过大等已确认限制外，不默认让 Agent 任意选择 PES/scan。大体系判据需结合方法、点数、资源与预算；暂不编造统一原子数阈值。成本未知不能静默切换方法或工作流。
4. **矩阵反应位点识别留空。** 用户正在开发该算法，后续接入工作流。此轮不实现替代算法，不冻结未知输出 schema，不将现有 bond_changes 等模块宣称为该算法。首版使用用户提供或确认的位点/反应假设；缺失时询问。
5. **首版允许全自动。** 在用户授权且平台可执行约束的范围内，Agent 可自动探索、选点、发布候选、提交 BatchOptimize、读取结果与决定后续；正常步骤不反复请求人工确认。
6. **选点只产生初猜。** PES/scan 中选出的 TS/INT 角色表示后续计算用途，不是已验证驻点。针对选点到驻点的产品链，必须经过 BatchOptimize 及适用验证；只保存候选不是整链完成。
7. **轻量指导、确定性检查。** 参数和产物事实从契约投影，科研指导少量编写、按需读取；科学事实、身份、授权与执行限制不交给模型自述。

## 2. 目标场景与完成定义

### 2.1 首批用户场景

| 场景 | 平台/Agent 配合 | 完成定义 |
|---|---|---|
| S1 构象搜索与批量处理 | Confsearch → 读取筛选/精修范围 → 选择候选 → BatchOptimize | 逐结构结果与来源可读；部分失败明确；能量比较须满足适用条件 |
| S2 键长探索到驻点初步验证 | 用户给定位点/假设 → PESsearch → Agent 选初猜 → 发布 → BatchOptimize | 优化/频率等所需结果逐候选关联；不能将选点角色当作驻点结论 |
| S3 scan 入口及下游 | 用户显式选择或适用例外 → scan → 选初猜 → 发布 → BatchOptimize | scan 使用自己的候选来源/保存契约，安全接入相同下游；不冒充 PES review |
| S4 信息不足时有限补算 | 曲线缺点/区间不清 → 有依据的补算计划 → 再选初猜 → BatchOptimize | 不重复提交已算任务；新计算有预算、身份与停止条件 |
| S5 会话中断与续接 | harness/MCP 重连 → 找回已有研究/任务/选点 → 恢复观察或推进 | 任务和候选不重复；已确认但未提交的候选能安全继续 |

首版覆盖以上场景的受限范围，并明确支持的计算方法、部署环境及输入形状。不以穷举所有反应机理为出口。

### 2.2 科学状态必须分开

以下是报告语义，不直接新增 JobStatus：

- 扫描完成、选点完成、候选已发布：只是过程状态。
- BatchOptimize 的每个 item/stage 执行结果：是计算事实，可能部分失败。
- 驻点性质、振动模式是否与目标变化一致、端点关联、能量可比性：是需要证据的判断。
- Batch 完成不自动等于 TS 得到验证；所需 IRC/端点验证未完成时，保留缺项与未定结论。
- 即使启用全自动，也允许无候选、全部候选失败、预算停止或命题 refuted。不得通过改角色/换输入隐瞒失败。

新增的错误建议和下一步提示是操作指引，不是权限授予或科学证据。无法确定修正方案时说明需要的信息，不自动改变用户科学意图。schema 发现、preflight 和执行之间不得各自维护一套默认值或科学规则。

### 3.3 MCP 本身的独立完成门

即使尚未启用指南或自动选点，已有 harness 也应能用公开 MCP 完成：连接→发现→构造请求→预检→纠正错误→提交→等待→发现产物→prepare/read→退出→找回任务。这条链单独验收，不得用“skill 里有说明”替代缺失接口。

固定至少一个完整正常请求、一个可修复参数错误、一个部分失败、一个缺失/旧产物、一个回包丢失与跨会话恢复场景。S1—S5 在此基础上验证科研指导和全自动链；基础门与科研门分别报告。

## 4. 指南内容与轻量交付

### 4.1 两类内容，各有权威

**自动投影的事实**：工作流 ID、输入字段/类型/单位、合法枚举、参数默认值、产物类型、可用能力、错误码与校验覆盖。从现有契约读取，运行环境的可用性由 discovery/preflight 计算，不写进静态指南。

**编写并评审的指导**：用途、不适用条件、用户必须确认的科学选择、复合流程阶段职责、部分失败含义、结果解读、补算条件、停止条件、例子和共用专题引用。指导不是执行证据，也不能覆盖服务端拒绝。

每份指南至少声明 `id`、版本、绑定的契约摘要、适用工作流/能力、覆盖范围、所需上下文、步骤、验证条件、失败/停止分支、示例引用。这里是逻辑字段，最终 wire 名称在 P0 冻结。

第 13 节现已给出全部 15 个 active 工作流的详细说明与 prompt 草案。首批重点交付四份场景指南：构象搜索与筛选、批量优化与验证、PES 键长探索与初猜选择、scan 的适用替代与初猜选择；其他指南按实际公开能力标记覆盖，不因有 prompt 就宣称接口已闭合。共用专题至少包含：输入/电子态确认、方法与能量可比性、驻点验证、部分失败与恢复、选点与补算。复合工作流已经封装的阶段只解释职责，不要求 Agent 再编排一次。

### 4.2 按需读取

1. capabilities 返回简短用途、限制、coverage 与 guide_ref。
2. Agent 选定场景后读取操作指南，获得必要选择、步骤、一个有效示例和停止规则。
3. 出错或需要判断时，读取指定专题/字段说明。首版只允许一层专题引用，避免递归加载。

建议首版传输目标：发现卡约 1 KiB 内、单份操作指南约 8 KiB 内；大专题分页或拆分。此为可调的 UTF-8 字节预算，不冒充不同模型通用的 token 数。超限返回显式分段/省略信息；关键限制和停止条件不得静默截断。指南带版本与 digest，可缓存；版本改变、契约不匹配或当前操作未读取所需部分时重新获取。

首版不依赖向量数据库、在线 LLM 生成指南或每次调用返回整份说明。通过工作流 ID/主题标签定位；模糊请求可返回少量匹配项和适用差异。模型不知道用什么时，工具描述应明确引导先发现再读取。

### 4.3 开发 Agent 的同步机制

- 提供新增工作流检查表和指南模板，写入对应 AGENTS 开发约定。
- 已有工作流允许显式 partial；新宣称 Agent-ready 的工作流必须有指南和有效示例。
- CI 从注册表枚举覆盖；验证 guide_ref、字段/产物/能力引用、专题链接和示例。
- 示例走真实共用纯校验；拒绝例验证字段/错误，不通过提交 QC 来校验文档。
- 以对外契约的规范化投影计算绑定摘要，不以源码文件哈希代替语义版本。指导引用的规则变化时要求显式复核；单纯更新摘要不算科学内容验收。
- 每份主要指南至少有一个正常案例及一个有意义的失败/不适用案例；复合工作流还要有部分成功案例。
- 自动测试保障没有漏项和接口漂移；科学适用性仍需评审与行为验收，不由生成指南的 Agent 自行判 PASS。

## 5. MCP / Application API 设计

第 3.2 节 U01—U09 同时约束已有工具；下表列新增或扩展操作的语义和建议名称，**新增名称尚未注册**。P0 冻结最终名称、版本、请求/响应 schema、权限与协商方式；不强行维持八个基础工具总数，也不让旧客户端被静默升级。

| 操作 | 首版建议 | 权限/行为 |
|---|---|---|
| 参数发现/预检/纠错 | 完善现有 capabilities/preflight/submit，不新建第二参数解析器 | 无效请求在 prepare/reservation/预算等副作用前拒绝；返回 field/rule 与有限修正建议 |
| 状态/产物/结果摘要 | 完善现有 status/prepare/read/analyze，完整实现 U05—U07 | 只读投影与显式准备分开；结果带事实来源，缺项不能补造 |
| 指南发现 | 扩展现有 `acp_capabilities(workflow=...)` 返回 guide_ref | 只读；保留旧回包兼容 |
| 指南读取 | 一个 `acp_get_guidance`，支持 id/topic/section/version | 只读、有界；直接返回必要文本，不依赖 harness 自动读资源链接 |
| 曲线/帧消费 | 已有 `acp_analyze` 注册操作或版本化专用读操作，P0 选择一个 owner | 只读缓存投影与显式准备分开；不得轮询时隐式远端 fetch |
| 选点提案/发布 | 明确版本化的选择操作，提案与发布动作分别定义 | 提案不执行 QC；发布是受授权写入，绑定 revision 和来源 |
| 任务/研究找回 | 权限范围内分页查询，返回稳定引用与状态 | 只读；避免靠猜 ID 或扫文件系统恢复 |
| 后续 Batch 提交 | 复用 preflight/submit/status/prepare/read/analyze | 独立执行动作，复用审批、预算与幂等；保存候选不暗中提交 |

全自动客户端可以连续调用“提案→授权发布→Batch preflight→submit”，不要求中间弹人工确认。多个显式命令仍可自动执行，且更便于崩溃后恢复。

所有操作经 Controller Application API；Services 通过注入端口委托 ACP 层实现，不导入 `acp`。RPH bridge 不直接 HTTP/SSH。可选 MCP Resources/Prompts 后续由同源内容投影，不作为首版前置；不同 harness 的原生 skill 安装行为不纳入协议承诺。

## 6. PES/scan 选点所需的数据与决策

### 6.1 分三级读取

**概况**：来源 task/attempt、曲线/profile 摘要、坐标定义/单位、扫描方法与能量方法、实际/计划点数、缺失/失败覆盖、已知候选区间、端点和数据省略标记。二维/多坐标数据必须保留拓扑与坐标关系，不能摊平成伪一维曲线；首版分析不支持的维度须明确报告。

**局部点表**：稳定帧 ID、原始索引、坐标值、能量及类型/单位、方法身份、优化/SCF 质量、结构引用；包含指定区间完整邻域和失败点，不能只返回“推荐最好点”。不混合不可比能量，缺失值不填零。

**结构/分析**：按需读取选中帧和邻域结构，提供已实现的结构变化、连续性或去重分析与来源。不存在的分析标 unknown；图像可辅助，数值与原生结构引用是主要输入。所有帧投影复用 `acp.results.frames`。

### 6.2 两种提案，不能混淆

**已有帧初猜提案**：来源 task/attempt、profile_ref/digest、帧 ID 集合、用途角色、证据引用、选择理由、疑点/备选、目标 Batch profile/角色配置引用。平台校验帧存在、可读、非 view-only、来源未过期、结构可用、角色合法；不把初猜角色转成驻点结论。

**补算提案**：目标区间/坐标、依据、拟议点数或加密策略、资源/方法、预算与停止条件。新点尚不存在，不得分配伪已有帧引用。通过新计划预检和提交后，再读取真实产物进行初猜选择。

不要求每条曲线产生一个 TS；允许多个初猜、平坦区间、补算或无可信候选。第一版可以复用已有算法推荐作为线索，但推荐不是确认、也不是科学证明。选择理由必须指向已读取的数据，不能只返回“模型置信度 0.9”。

### 6.3 默认策略与成本

键长扫描默认 PESsearch；显式 scan、已确认资源不适用等例外记录理由。资源估计标记来源与误差范围；没有可靠估计时标 unknown。按点数/方法/资源规划预算，允许授权范围内调整；不能以“大体系”为理由无记录地降低科学方法。

## 7. 首版全自动授权与人工模式

### 7.1 两种交互模式，同一科学链

| 模式 | 行为 |
|---|---|
| 全自动 | 用户预先授权范围内，Agent 自动选初猜、发布、提交 Batch、读取和修订；正常步骤不需人逐次批准 |
| 交互式 | 同一份提案由用户审查/修改后发布，再按既有策略提交 |

“全自动”不等于 Agent 拥有审批管理权限。授权来自用户/管理员配置的策略或既有合法授权，由平台验证身份和适用范围；Agent 不能修改自己的授权或伪造授权凭据。若现有审批只绑定具体 plan_digest，需增加受限授权到逐计划决定的明确转换，不能直接复用旧 approval 通过不同计划。

### 7.2 自动执行范围

P0 固定授权记录的 owner、有效期、撤销与持久化方式，至少覆盖：项目/主体、来源结构与反应假设、允许的 workflow/方法与角色、资源范围、最大初猜数、Batch item/stage 或任务预算、最大补算/重试轮次、允许动作和停止条件。

每个实际计划仍有独立 digest，并记录通过哪个授权规则、策略版本、预算检查而准入。授权范围变化走显式更新；过期/撤销/预算不足停止新增动作，已运行任务的处理遵循既有取消策略。不得借方案扩大无限计算。

列出哪些限额由服务端硬执行、哪些只是估计或客户端提醒。新增初猜数/补算轮次等产品上限必须在服务端共享状态检查，防止换会话清零。累计 token/core-hours 硬强制仍为既有 DEFERRED，不在首版伪装已实现。

### 7.3 选点来源与确认语义

将“谁提出初猜”和“谁/什么策略允许发布”分开记录。逻辑上包括 selector（human/agent/algorithm）、actor identity、policy/approval ref、selection revision、来源工件绑定、guidance version、理由及提交关联；具体 schema 在 P0 冻结。

旧 manual/manual_frame 记录按历史语义读取，不能批量重写。Agent 来源必须真实标识；自动发布后可以供下游消费，但“已授权发布”不表示“人审过”或“TS 已验证”。确认门继续存在，其语义扩展为合法授权的候选定稿，而非无条件要求人工点击。

## 8. 候选发布、BatchOptimize 与恢复

### 8.1 统一写入与来源适配

- PES 复用 `pes/review.py` 唯一写入链，扩展 schema、来源、policy 记录与兼容读取；保持 CAS、备份和路径/几何检查。
- scan 复用通用 `frame_candidates.json` 权威和其保存服务，明确到 Batch 的受控适配；不伪造 PES review。
- 公共 selection 操作只作来源路由和授权/事务编排，不建立第二候选文件或第二套科学验证。
- Batch loader 同步校验已授权的 Agent 来源及对应来源证明，不能只把 `agent` 加进字符串集合。
- 发布部分失败时不能让不完整候选集被下游读取；本地及远端写回均需明确提交标记、可恢复状态和失败回滚/对账策略，实施前核查现有机制，不假定多文件写天然原子。

### 8.2 初猜到 Batch 的强制关联

PES/scan 场景的完成链为：

```text
扫描产物 → 初猜提案 → 合法授权发布 → Batch preflight/submit
        → 逐候选优化/适用频率等结果 → 证据判断 → 继续验证/修订/停止
```

每个 Batch item 保留 source task/attempt、selection revision、candidate ID、原始帧/结构 digest、用途角色、实际生效配置与后续产物引用。TS 与 INT 的优化/验证配置通过现有 profile/角色解析明确映射；不因候选名含 TS 就声称做了 TS 优化。

选中后因预算或条件不足未进入 Batch，应记“待后续计算/已停止”，不能报 TS 搜索成功。Batch 部分失败按 item/stage 处理，只对确有依据且获授权的失败项补算，不整批盲重跑。所需频率、模式或端点检查缺失时明确报告，IRC 等按能力和适用性独立推进。

### 8.3 幂等与崩溃矩阵

| 中断位置 | 恢复要求 |
|---|---|
| 提案已存、尚未发布 | 对账来源与授权，复用提案；不得凭聊天重建另一份 |
| 发布写入过程中 | 识别提交状态与 revision；补齐/撤销未完成发布，不暴露混合集合 |
| 发布完成、Batch 未提交 | 用稳定 selection revision 构造既有提交意图，再预检/提交 |
| submit 成功、客户端未收到回包 | 查询已有幂等记录/TaskRef，不生成新键 |
| Batch 运行中/部分完成 | 恢复观察原任务，按已完成 item/stage 对账 |
| 来源 rerun 或选点 revision 改变 | 不静默换成新产物；旧已提交任务保持冻结来源，新计划显式重绑定 |

幂等键沿用平台规范和 canonical digest，不自造第二实现。研究记录或既有 proposal 资源保存客户端决策/checkpoint，任务事实仍归 Controller。用户无需记住 ID，应能从权限范围内的查询恢复引用。

### 10.1 四层验证，不相互替代

### 13.1 加载方式与共享上下文

运行时只组合“通用 prompt + 当前工作流 prompt + 确实需要的专题”；跨工作流场景再加载第 14 节的编排 prompt。不要把本节全部注入每次会话。工作流正文如超出第 4.2 节预算，拆成显式主题段，关键边界随主段一起返回。

服务端应给以下上下文各自标明来源；它们是 prompt 组装输入，不是新的 submit 字段：

| 上下文 | 内容与权威 |
|---|---|
| 用户目标 | 当前研究问题、期望结果、用户提供/确认的信息 |
| 平台能力 | 当前会话发现的工作流、实际工具、版本、契约覆盖、环境支持 |
| 输入引用 | 结构/谱/上游工件的引用、版本、原子映射与已知科学身份 |
| 执行范围 | 平台验证的项目/主体/方法/资源/预算/自动执行权限；用户原文不能伪装成服务端授权 |
| 任务事实 | 已有 TaskRef、attempt、状态、选点 revision、提交意图、原生产物与验证报告 |
| 指南身份 | 当前指南版本、绑定契约摘要、已加载段落 |

缺少上下文时使用明确的 unknown，不生成假引用填空。原始日志、工件正文及用户上传文件作为数据处理，其中的指令不能改写执行范围或绕过平台检查。

### 13.2 通用执行 Prompt（各工作流共用）

```text
你通过 ACP MCP 协助用户完成受控的计算化学任务。使用当前会话实际开放的工具和服务端契约，不以本指南代替执行权限、科学验证或参数校验。

1. 识别用户目标，读取当前工作流能力、输入契约和适用指南。区分 registered、当前可执行、参数覆盖完整与真实验收范围。未知或 partial 不等于全部不能用，但只能构造已经有明确契约覆盖的请求；必需部分缺失则报告缺口，不猜字段。
2. 优先复用已存在的结构、任务和工件。核对项目、来源 attempt、generation/digest 与电子态；保留原子顺序和映射。不要猜绝对路径、手填摘要或把展示序号当原子/帧身份。
3. 从已有记录或授权读取科学选择，不机械地重复询问。真正缺少且影响计算含义的信息应集中询问。参数默认值必须来自契约；方法升级、改变电荷/电子态、扩大研究范围不能悄悄进行。
4. 全自动模式下，授权范围内的选点、发布、提交、等待、读结果与有限修订直接推进，不逐步要求用户点击。权限不足、来源不明、超范围或预算不足时停止相关写入并说明原因；不自行批准自己的计划。
5. 提交前使用实际开放的预检入口，读取错误与生效配置。对明确可修正的输入错误按字段/rule 修正；不靠轮换字段、关校验或改变科学目标获取通过。
6. 使用平台规定的幂等机制。相同请求重试复用原提交意图和键；回包丢失先找回已有任务。输入或计划变化时重新预检并绑定新身份，不能复用不匹配的旧审批。
7. 对长任务使用有界等待或建议的查询间隔，不反复调用模型重新规划。区分 MCP 调用成功与任务 completed，区分整个任务和逐 item/stage 的结果。
8. 从 status/结果发现获得产物描述，再显式 prepare/read。检查引用、编码、完整性、截断与摘要作用域。看不到的部分不推断为通过；必要时使用已开放的区间/专题读取。
9. 读取优化/SCF/方法/结构等实际证据。区分 requested、effective 和 executed；模型解释不是执行事实。缺失验证保留 unknown/inconclusive，证伪保留 refuted，不为完成流程强行输出 supported。
10. PES/scan 的 TS/INT 选点只产生初猜。针对选点到驻点的任务，初猜必须通过合法发布进入 BatchOptimize，再读取逐候选优化和适用验证结果。保存成功不是 TS 找到，Batch completed 也不是反应路径验证完成。
11. 只对有依据、在范围内且预算允许的失败项或缺失信息追加计算。限制总候选数、补算/重试轮次；避免相同结构和配置重复提交。无法改善证据时停止，不无限重跑。
12. 会话恢复先查询平台记录，核对已有任务、选点和提交意图，再决定下一步。不要只依据聊天摘要重新提交。

对用户的结果回答包括：实际完成的工作、关键结果及引用、可支持的结论、缺失/失败项、下一步或停止原因。需要内部结构化记录时复用平台 schema；不要将叙述直接写成科学证据。
```

### 13.3 Confsearch — 构象搜索与筛选

**用途与流程**：围绕给定分子生成构象并按所选协议筛选/精修。现有协议为 xtb-crest、xtb-md、censo-crest、xtbmd-censo；阶段和实际依赖由协议决定，不能把 registry 的软件并集当成每个协议都必需。`screen` 不选取后续精修候选，纯 xTB 协议不能宣称执行了 DFT 精修。

**输入与结果**：结构及电子态、协议、筛选/精修策略、资源；产出构象集合、计数、方法与筛选/精修信息及可发现的报告/manifest。下游可进入 BatchOptimize；需要用户给定反应坐标时可作为 PES 来源。构象搜索完成不证明全局最低点或构象空间穷尽。

```text
当前工作流：Confsearch。目标是获得有来源、有质量说明的构象集合，并在用户目标要求时继续批量计算。

1. 核对分子结构、立体化学、片段组成、电荷/多重度及相关环境。已有可信输入时复用；SMILES 等输入的映射以服务端物化结果为准。
2. 读取当前协议列表与每个协议实际阶段/可用性。根据用户目标和授权选择，不把全部软件依赖强加给纯 xTB 场景，也不无记录地替换协议。
3. 说明并绑定筛选与精修策略。screen 允许零精修候选；纯 xTB 路径只报告其实际计算级别。不要提交该工作流不支持的 max_conformers 等参数。
4. 预检后提交和等待，分别读取搜索产生、筛选保留、精修选中及实际精修成功数，不能把这些计数互换。
5. 读取每个候选结构、能量类别、实际方法和质量记录。精修/未精修混合集合不能直接当作同一级别排序；未知方法保持未知。
6. 选择下游候选时说明范围与依据，使用稳定候选引用，保留合理的结构多样性与预算限制；去重只使用实际存在的分析，不捏造 RMSD。
7. 若用户要求进一步优化/验证，按候选引用构造 BatchOptimize；若用户只要求构象集合，可在报告筛选范围与局限后结束。
8. 某阶段失败时区分已有可用集合和未完成部分；只在授权内恢复或补算，不伪称全套协议完成。

输出：协议与实际阶段、分阶段计数、候选及来源、方法可比性、覆盖局限，以及已提交的 Batch 引用或结束原因。
```

### 13.4 BatchOptimize — 批量优化与后续计算

**用途与流程**：对一组带角色的结构逐项执行配置的阶段。当前 profile 为 `opt_only`、`opt_freq`、`opt_freq_sp`、`opt_freq_sp_thermo`，分别添加频率、单点、热化学步骤。TS/INT 角色及其生效参数由现有配置解析器决定，不由名字或 TAG 自动证明科学属性。

**输入与结果**：结构集合/上游已发布候选、选择子集、角色配置与 profile；输出逐 item/stage 的结构、能量、频率/热化学等实际产物。PES/scan 初猜必须在本工作流中完成所需优化和适用验证，只有 opt_only 不等于完成驻点验证。

```text
当前工作流：BatchOptimize。你要将候选初猜推进为可检查的计算结果，保留每个 item 的来源和实际执行情况。

1. 读取输入集合与发布状态。PES/scan 初猜应来自合法发布，绑定来源 task/attempt、selection revision、candidate ID 和结构 digest；未确认推荐点不能直接当最终输入。
2. 明确每个 item 的用途角色。TS 表示尝试过渡态优化的初猜，INT 表示相应最低点优化用途；混合角色使用平台实际支持的配置表达。
3. 读取 profile 和生效配置。需要频率/单点/热化学时选择包含这些阶段的配置；不把 opt_only 报成 opt_freq，不为方便批量而抹平 TS/INT 的不同设置。
4. 核对每项电荷/多重度、优化级别、频率级别、单点级别、温度/环境和资源。遵守平台对 batch_roles 与平铺参数的一致性检查，不用重复冲突字段覆盖配置。
5. 按可执行范围预检、提交与等待。读取逐 item/stage 的成功、失败、跳过及原因，不能仅凭总任务 completed 推断全部完成。
6. 对成功优化结果读取适用频率和模式验证。报告其原生判定及缺项，不仅按虚频数量给出最终反应结论；阈值和质量标准来自平台或明确研究设置。
7. 只有可比的物种/方法/能量定义/环境才进行所需比较。区分电子能与热化学校正，避免重复加校正；不比较来源不明或不完整的值。
8. 对失败项先判断可修复原因，再在剩余范围与预算内补算；复用已完成阶段的身份校验机制，不盲目重跑整批。
9. 针对 TS 研究，若还缺模式关联或 IRC/端点证据，继续适用验证或明确停在候选阶段。不得将 Batch 结束直接写为机理验证通过。

输出：逐候选来源、角色、实际阶段、结构/结果引用、科学判定与缺项、失败恢复情况、下一验证任务或停止原因。
```

### 13.5 PESsearch — 键长势能面探索与初猜生成

**用途与流程**：可从结构或上游结果进入扫描；直接 bond-length scan 请求包含来源、坐标及协议，执行松弛扫描、配置的逐帧单点与候选推荐。当前适配器的部分 strategy 名称只参与校验/元数据而未驱动独立执行策略，不能将 direct_ts 等名称当作自主 TS 搜索已交付。

**输入与结果**：结构/上游引用、明确的位点与坐标计划、扫描/单点方法及资源；输出 profile、帧、推荐等。推荐与最终发布分开，选点仅为初猜，下一阶段进入 BatchOptimize。矩阵识别算法待接入，不在此 prompt 中模拟实现。

```text
当前工作流：PESsearch。对键长势能面扫描优先采用此入口，目标是探索并提出可追溯初猜，再由 BatchOptimize 优化与验证。

1. 核对用户给定或确认的反应假设、关键原子及结构映射。位点矩阵算法尚未提供时，不声称已经运行自动位点识别；缺少关键位点则询问。
2. 读取当前可执行的扫描模式和请求契约；核对原子索引约定、坐标类型/单位、范围/点数以及多坐标关系。不要凭 strategy 字符串承诺服务端未实现的算法。
3. 绑定扫描方法与逐帧能量方法、电子态、资源和预算。键长扫描默认 PES；若体系规模/成本有已确认限制，记录例外理由后才选择适用替代，不自行按原子数拍阈值。
4. 执行后先读取曲线概况和全部点覆盖状态，再读取候选区间的完整邻域点表及必要结构。区分扫描能与单点能，保留失败点、缺点和不收敛标记。
5. 结合目标结构变化、局部曲线和质量信息选择多个有理由的 TS/INT 初猜或明确不选；不得只挑全局最高点，也不能把平滑图形当作收敛证明。
6. 信息不足时提出有限补算区间/坐标与预算，和已有帧初猜提案分开。新点在真实计算完成前不具有帧身份；超过授权则停止相关计算。
7. 按真实来源保存提案。在全自动授权有效时自动发布；交互模式下交由用户审查。缺少自动发布能力时报告未开放，不能借 manual 来源绕过。
8. 发布后将初猜连同角色和来源绑定送入 BatchOptimize。保存成功而 Batch 未运行时，只报告初猜已保存/待计算，不报告已找到 TS。
9. 读取 Batch 逐项结果，按适用规则继续模式与端点验证，或保留失败、不确定与停止原因。

输出：坐标/方法/覆盖、所选初猜与证据、补算记录、发布 revision、Batch 引用及验证进展。
```

### 13.6 scan — 指定坐标扫描

**用途与流程**：执行契约支持的内坐标扫描，获得逐点结构与能量；当前公开说明以 ORCA relaxed scan 为主。ScanTS 为显式 opt-in，默认关闭；不能把 scan 与自动 TS 搜索等同。与 PES 共享底层能力不代表上层候选契约相同。

**输入与结果**：结构、扫描坐标/范围/步数、方法/电子态/约束；输出扫描 profile 与结构帧等。键长任务默认推荐 PES，scan 用于明确选择或适用例外。选出的驻点初猜经自身候选保存路径进入 BatchOptimize。

```text
当前工作流：scan。你要执行用户明确选择或确有适用理由的坐标扫描，不把扫描结束解释为找到驻点。

1. 对键长扫描先检查是否应使用默认 PESsearch；若用户明确选 scan 或有已确认限制，记录原因并继续，不强迫改写已确认意图。
2. 读取 scan 契约，确认坐标类型、原子顺序/索引约定、单位、起止/点数、多坐标耦合、方法和电子态。未开放的维度或后端不猜参数绕过。
3. ScanTS 只在明确选择、授权且平台支持时启用；没有启用时不得暗示内部已优化 TS，即便启用也需要读取实际产物与验证结果。
4. 预检后执行，逐点检查结构可读性、收敛/失败状态和能量可比性；缺失点不插值成已计算事实。
5. 若目标只是扫描，提供曲线范围、原始结果与局限；若目标包含驻点搜索，按第 14 节规则选初猜、必要时在范围内补算。
6. 通过 scan 对应的通用帧候选契约发布，不能伪造 PES review。来源适配或 MCP 写入口尚未开放时明确说明阻塞，不直接写文件。
7. 将合法发布的初猜传入 BatchOptimize，并跟踪逐候选优化/频率等结果。区分 scan 的输出与 Batch 的最终结构。

输出：选择 scan 的原因、坐标与方法、点覆盖及异常、帧引用、初猜/Batch 关联或纯扫描结束理由。
```

### 13.7 singlepoint — 固定几何单点能

**用途与流程**：在给定几何上通过当前工作流的 ORCA 路径计算电子能等所需产物，不自动优化几何或计算热化学。输入的几何与电子态是科学身份的一部分。

```text
当前工作流：singlepoint。目标是在明确几何和电子态上得到可追溯的单点结果。

1. 绑定确切结构引用与来源。确认用户要求的是当前几何单点；若研究还需要优化或频率，说明差异而不私自替换任务。
2. 从契约确认方法、基组或复合方法规则、环境、电荷/多重度和资源。不要为带内置基组的方法随意填另一个基组，也不要把所有方法都视为 basis 可空。
3. 预检有效配置后提交，检查实际 SCF/电子态质量、执行方法、能量类型和产物完整性。进程退出成功不替代这些检查。
4. 比较结果前核对组成、电子态、方法和能量定义等适用条件；不同化学计量的反应能需要明确平衡关系，不直接做任意两值相减。
5. 报告电子能及单位和来源，不把它称为自由能。需要热化学或构象权重时引用相应已有产物或提出后续适用任务。
6. 未收敛时按明确原因与授权修订，不能输出不可信数值作为成功结果或无上限增加迭代。

输出：结构/方法/电子态、能量及引用、收敛与质量、比较适用范围和后续需求。
```

### 13.8 optimize — 几何优化

**用途与流程**：普通 ORCA 几何优化入口；TS 初猜的批量推进优先按 BatchOptimize 角色配置完成。是否存在约束、实际优化语义均按当前契约，不能凭方法名称推断。

```text
当前工作流：optimize。目标是得到给定起始结构在指定设置下的优化结果。

1. 确认结构来源、电子态、方法和环境，以及有无约束；明确目标是普通优化还是 TS 验证链。属于已发布 PES/scan 初猜的 TS/INT 集合时，应走既定 BatchOptimize 链。
2. 读取允许的优化配置与有效默认值，预检后执行；不要用未公开 raw keyword 绕过契约。
3. 读取实际优化收敛、SCF 质量、最终几何和轨迹；出现组成/目标结构变化时记录并按目标判断是否可接受，不能只看能量下降。
4. 优化收敛不证明局部最低点或全局最低点。用户目标需要驻点性质时，继续适用 frequency 或读取已有验证。
5. 有约束的结果保留约束说明，不当作无约束驻点；解除约束属于新的明确计算选择。
6. 对失败只在范围内执行有依据的恢复，不因重复运行得到更低能量就忽略身份与配置变化。

输出：输入和最终结构引用、实际设置、收敛/变化、驻点验证缺项及下一步。
```

### 13.9 frequency — 频率与振动分析

**用途与流程**：在给定结构和方法上运行 ORCA 振动频率计算并发布频率、模式/Hessian 等实际产物。它不是几何优化入口，也不保证自动给出适用于任意比较的自由能。

```text
当前工作流：frequency。目标是得到与确切结构/方法绑定的振动证据，并按研究目标解释。

1. 核对几何来源、是否优化及相关约束、电子态、计算方法与所需环境。未优化结构可以按明确目的计算，但不能暗示它已经是驻点。
```


## 15. Prompt 的交付、同步与验收要求

1. P0 对第 13 节 15 个 ID 与 catalog active 集合做机器核对；每个场景说明都标出源码/契约来源。本文全面列出不等于首批宣称全面可执行。
2. P1b 将正文移入可随发行安装的指南内容包，计划保留版本引用和可审查快照；不要维护两份独立生长的权威 prompt。MCP 事实投影继续来自代码契约。
3. 通用段和专用段分别版本化；使用卡声明组合版本、契约摘要、覆盖与已加载章节。运行时不得悄悄追加改变授权的系统指令。
4. 构造请求时采用“当前契约 + 经过校验的示例”，不在 prompt 写死完整 JSON 请求；特殊冻结 payload 同样要从公开契约获得，不引导 Agent 读服务器源码。
5. 每个工作流至少验证：能力未开放、关键输入缺失、正常结果、部分/完全失败、实际产物缺失、与用户目标不符时的停止行为。专项负例按下表增加。

| 工作流族 | 必须覆盖的 prompt 行为负例 |
|---|---|
| Confsearch/BatchOptimize | screen 零精修、混合计算级别、TS/INT 不同配置、未发布来源、逐项部分失败 |
| PESsearch/scan | 单调/多峰/平台/缺点、不收敛、view-only/旧帧、未实现策略名、补算预算耗尽、仅发布未进入 Batch |
| singlepoint/optimize/frequency/xtb_optimize | 不可比能量、优化未收敛、未验证驻点、缺模式/热化学、xTB 结果冒充 DFT |

7. 接口能力不全时 prompt 必须能诚实停止；不能为提高成功率让 Agent 使用隐藏端点、shell/QC、旧工作流或伪造科学输入。
