

ACP RI 加速与辅助基组配置重构 — 开发文档

版本：v1.3 · 2026-07-21

涉及模块：src/acp/catalog.py · src/acp/cli.py · src/acp/workflows/energy.py · src/acp/workflows/simple.py · src/acp/api/v1_routes.py · src/acp/scheduler/store.py · src/cccp/qc/interfaces/orca.py · frontend/ACP_Workbench_v2.html · tests/

本文档定义 ACP 平台 RI 加速配置与辅助基组体系的完整重构方案。核心动机：当前 supports_ri: bool 字段无法区分"复合方法内置 RI"、"普通杂化可选 RI"、"DLPNO 自动 RI"三种语义；aux_basis 单字段无法表达双杂化同时需要的 /J 和 /C 辅助基组；ORCA 输入生成将辅助基组名错误地拼接到 ! 行而非独立的 %basis 块。

⚠️ 本次重构 破坏向后兼容：移除 supports_ri 字段；将 aux_basis 拆分为 aux_j_basis + aux_c_basis；API basis_catalog 字段类型从 array 变为 object。已保存的 job 配置中残留的旧字段由后端兜底迁移逻辑处理（详见 §6.5 + §6.7）。

详细开发步骤（v1.1 新增）

1. 背景与问题

1.1 现状概述

ACP 平台当前对 ORCA 的 RI（Resolution of Identity）加速配置散落在多个层次，语义割裂、字段冗余、用户感知混乱。主要问题如下：

 | 问题 | 表现 | 代码位置

 | 字段语义错位 | supports_ri: bool 把 3c 复合方法（r2SCAN-3c 等）与 DLPNO-CCSD(T) 都标记为 False，但二者实际行为截然不同 | catalog.py:211-325 METHOD_META

 | 单字段无法表达双需求 | aux_basis 单字段对双杂化泛函（PWPB95/wB97M-2）无法同时承载 /J 和 /C 两类辅助基组 | catalog.py:465-477 FIELD_DEFINITIONS

 | 字段暴露不足 | RI 字段仅出现在 single_point level，opt/freq 级别（计算量最大、最需 RI）反而无此字段 | catalog.py:500-516 等多个 SCHEMAS

 | 默认值不一致 | 内置 profile 中 aux_basis="" 且 ri_approximation 缺省；CLI --ri-approximation 默认 "none"；catalog 默认 "RIJCOSX" | catalog.py:571-579, cli.py:252, catalog.py:476

 | ORCA 输入错误 | 辅助基组名（如 def2/J）被拼接到 ! 行而非独立的 %basis 块 | orca.py:217-219（extras_str 拼接）

 | def2 /J 命名错误 | 原方案草稿误写 def2-SVP/J、def2-TZVP/J，ORCA 中只存在唯一的 universal def2/J | （已在方案修订中修正）

1.2 后端实际行为（关键洞察）

src/cccp/qc/interfaces/orca.py:161-219 显示，ORCA 后端完全不读 supports_ri 字段。它依据 basis_inline + basis_block 两个字段做分派：

 | 方法类型 | basis_inline | basis_block | ORCA 输入渲染 | RI 关键字行为 | aux_basis 消费

 | 3c 复合方法
（r2SCAN-3c/PBEh-3c/B97-3c） | False | 无 | ! r2SCAN-3c Opt <extras> | 用户传 RIJCOSX 会被塞进 extras → ORCA 报错或忽略 | 完全不被消费

 | 普通/范围分离杂化
（B3LYP/PBE0/M062X/wB97X-D4/wB97M-V） | True | — | ! B3LYP def2-TZVPP Opt <extras> | extras 接收 RIJCOSX/RIJK + /J 辅助基组 | 原样追加到 extras

 | 双杂化
（PWPB95/wB97M-2） | True | — | 同上 | 需要 RIJCOSX + /J + /C（RI-MP2 需要） | 同上（单字段无法表达双需求）

 | 后 HF（DLPNO-CCSD(T)） | False | 有 | ! DLPNO-CCSD(T) TightSCF Opt <extras> + %basis auxJ/auxC | 用户传 RIJCOSX 多余（DLPNO 自带 RI） | 覆盖 %basis auxC（有意义）

1.3 def2 /J 辅助基组的真相

ORCA 中 def2 系列的 /J 辅助基组只有一个：def2/J（Weigend universal fitting basis, Phys. Chem. Chem. Phys. 2006），适用于所有 def2 主基组以及任何其他主基组。不存在 def2-SVP/J、def2-TZVP/J 这样的变体。

相反，/C 辅助基组（用于 RI-MP2/DLPNO 等波函数方法的相关拟合）才有逐级配对：

def2-SVP/C、def2-TZVP/C、def2-TZVPP/C、def2-QZVPP/C（Weigend, Köhn, Hättig, J. Chem. Phys. 2002）

cc-pVDZ/C、cc-pVTZ/C、cc-pVQZ/C、cc-pV5Z/C（Dunning 系列 /C）

aug-cc-pVDZ/C、aug-cc-pVTZ/C、aug-cc-pVQZ/C（扩散aug- Dunning /C）

2. 核心设计决策

2.1 设计哲学

核心原则：基组定义自身携带其辅助基组配对元数据（J/C），让前端从主基组直接派生辅助基组选项。新增基组接入零成本——仅需在 BASIS_CATALOG 中加一条记录。

2.2 五大设计支柱

 | 支柱 | 设计 | 替代的原方案

 | BASIS_CATALOG 字典化 | 每个主基组携带 aux_j + aux_c 量身定制配对信息（或 None） | 原扁平 tuple _ALL_BASIS_SETS

 | METHOD_META 三态化 | supports_ri: bool → ri_support: "composite" | "user" | "automatic" + needs_aux_c: bool | 原二值布尔无法区分复合方法与 DLPNO

 | aux_basis 字段拆分 | 单字段拆为 aux_j_basis + aux_c_basis | 原 aux_basis 对双杂化无法表达 /J + /C 双需求

 | %basis 块统一生成 | 所有方法路径统一通过 %basis auxJ/auxC 块消费辅助基组 | 原普通 DFT 把辅助基组拼到 ! 行（错误）

 | composite 守护层 | ORCAInterface 检测到 composite/automatic 方法时过滤 route_extras 中的 RI 关键字 | 无守护，依赖前端隐藏字段（不可靠）

2.3 决策矩阵（基于多轮讨论）

 | 决策点 | 选择 | 理由

 | 字段暴露范围 | 扩展到所有 ORCA level（opt/freq/SP） | ORCA 习惯：opt/freq 计算量最大，RI 收益最高

 | 3c 方法语义 | 引入 ri_support 三态取代 supports_ri 布尔 | 三态可准确区分复合方法、用户可选、自动 RI

 | aux_basis 设计 | 拆为 aux_j_basis + aux_c_basis | 双杂化同时需要 /J 和 /C，单字段无法表达

 | UI 交互模式 | 保留两个下拉（不引入总开关） | 高级用户保留全部选项的灵活性

 | CLI 默认值统一 | 全部对齐 RIJCOSX | 支持 RI 的泛函默认开启加速

 | 向后兼容策略 | 直接拆掉 supports_ri（不留派生属性） | 一次性迁移，避免长期技术债

 | aux_basis 选项分流 | BASIS_CATALOG 元数据驱动（不硬编码分组列表） | 新基组接入零成本，单一数据真相

 | DLPNO aux_basis 可见性 | 隐藏（auxC 固定由 profile 提供） | 保持当前行为；c_dlpno 分组保留供未来开放

 | composite 守护尺度 | 保守过滤（明确集合 + /J /C 子串启发式） | 保留 VeryTightSCF 等无关 extras

 | Dunning /J 策略 | aux_j=None（无量身定制，用 AutoAux） | Dunning 系列无量身 /J，保持诚实

3. BASIS_CATALOG 字典化

3.1 数据结构

替换 catalog.py:182-191 的扁平 tuple，引入带元数据的字典。

v1.1 化学事实修订（基于可行性评审）：

def2-SV(P)/C 不存在 — Weigend/Köhn/Hättig JCP 2002 系列只发表 SVP/C 及以上；ORCA 中指定会报错。改为 None（→ AutoAux）。

PD 变体（TZVPPD/QZVPPD）保留复用父级 /C 的 pragmatic 选择，但 option_meta 中明示精度折衷。

3c 方法使用的基组（def2-mTZVPP / def2-mSVP / mTZVP）补全到 catalog，避免前端 basisCatalog[basis] 查找返回 undefined。

3.3 验证依据

def2/J 唯一性：Weigend PCCP 2006 — "a universal auxiliary basis set for all basis sets of the def2 family"

def2 /C 系列：Weigend, Köhn, Hättig JCP 2002 — 系统发表 SVP/C ~ QZVPP/C（不含 SV(P)/C）

Dunning /C 系列：Woon & Dunning JCP 1995 — cc-pVnZ 系列 /C

cc-pwCVnZ / cc-pCVnZ 无 /C：用户确认（ORCA 中不存在量身定制的 /C 辅助基组）

ma-def2 不复用父级 /C（v1.1 修订）：Zheng et al. JCTC 2011 — ma- 加扩散函数，父级 /C 缺扩散拟合；推荐 AutoAux

PD 变体复用父级 /C：Hättig PCCP 2005 — def2 系列设计允许同 zeta 数 /C 复用（精度损失 <0.1 kcal/mol for typical single-points）

v1.1 自检关卡（Phase 0a 必跑）：BASIS_CATALOG 实施完成后，立即运行 tests/test_acp_catalog.py::test_basis_catalog_orca_keyword_existence（详见 §12.1），对每个非 None 的 aux_j/aux_c 值做 ORCA 关键字存在性断言，避免错误数据向下流污染解析器与 UI。

5. FIELD_DEFINITIONS 拆分

5.1 替换原 aux_basis 字段

def normalize_legacy_method(method: dict[str, Any]) -> dict[str, Any]:
    """读时归一化：把 v1.0 旧字段转换为 v1.1 的字段结构。

    操作 JobSpec.method 字典中的 levels 子字典。幂等：已经是新结构
    的 method 无副作用返回。供 store._row_to_record 调用，避免反向
    依赖（catalog 是底层模块，scheduler 依赖它合理，反之不然）。
    """
    if not isinstance(method, dict):
        return method
    levels = method.get("levels")
    if not isinstance(levels, dict):
        return method
    for level_id, level in levels.items():
        if not isinstance(level, dict):
            continue
        # aux_basis → aux_j_basis / aux_c_basis（逻辑与 _clamp_to_functional 一致）
        if "aux_basis" in level and "aux_j_basis" not in level and "aux_c_basis" not in level:
            func = level.get("functional")
            meta = _case_insensitive_get(METHOD_META, func) if func else None
            ri_support = (meta or {}).get("ri_support", "user")
            if ri_support == "automatic":
                level["aux_c_basis"] = level.pop("aux_basis")
            else:
                level["aux_j_basis"] = level.pop("aux_basis")
    return method

                    return basis_meta["aux_c"]

        if field_name in ("basis", "dispersion"):
            mapping = _case_insensitive_get(FUNCTIONAL_OPTIONS_MAP, functional)
            if mapping and field_name in mapping:
                opts = mapping[field_name]
                if opts:
                    if global_default and global_default in opts:
                        return global_default
                    return opts[0]

    return global_default

def _resolve_field_options(
    field_name: str, engine: str, functional: str | None = None,
    basis: str | None = None,   # 新增
) -> list[str] | None:
    if functional and field_name in ("basis", "dispersion"):
        mapping = FUNCTIONAL_OPTIONS_MAP.get(functional)
        if mapping and field_name in mapping:
            return mapping[field_name]

    fd = FIELD_DEFINITIONS.get(field_name)
    if not fd:
        return None

    # ── 动态 aux_j_basis / aux_c_basis 选项 ──
    if field_name in ("aux_j_basis", "aux_c_basis") and fd.get("options_source") == "dynamic_aux_basis":

        fallback = fd.get("per_backend", {}).get(engine, [])
        if not isinstance(fallback, list):

        # 从 BASIS_CATALOG 注入当前 basis 的量身定制项
        if basis and basis in BASIS_CATALOG:

        return fd["options"]
    if "per_backend" in fd:
        opts = fd["per_backend"].get(engine, list(fd["per_backend"].values())[0] if fd["per_backend"] else [])
        if opts is _BASIS_CATALOG_REF:
            return list(_ALL_BASIS_SETS)
        return opts
    return None

11.1 getFieldDefault 升级（行 3518-3544 + 行 4003 嵌套版） v1.2 补全

function getFieldDefault(catalog, fieldName, engine, functional, basis) {
  var fieldDefs = (catalog && catalog.field_definitions) || {};
  var methodMeta = (catalog && catalog.method_meta) || {};
  // v1.1: 优先读 basis_catalog_v2（object），降级到 basis_catalog（v1.0 兼容）
  var basisCatalog = (catalog && catalog.basis_catalog_v2) || {};

  // ── Priority 1: functional-level defaults ──
  if (functional) {
    var funcMeta = lookupCI(methodMeta, functional);
    if (funcMeta) {
      var riSupport = funcMeta.ri_support || "user";

      // composite / automatic：ri 和 aux 字段返回 none / ""
      if (riSupport !== "user") {
        if (fieldName === "ri_approximation") return "none";
        if (fieldName === "aux_j_basis") return "";
        if (fieldName === "aux_c_basis") return "";
      }

      // aux_j_basis：从 BASIS_CATALOG 派生
      if (fieldName === "aux_j_basis" && basis && basisCatalog[basis]) {
        return basisCatalog[basis].aux_j || "AutoAux";
      }

      // aux_c_basis：仅 needs_aux_c 时返回非空
      if (fieldName === "aux_c_basis") {
        if (!funcMeta.needs_aux_c) return "";
        if (basis && basisCatalog[basis]) {
          return basisCatalog[basis].aux_c || "AutoAux";
        }
      }

      // basis / dispersion 默认（保持不变）
      if (fieldName === "basis" && funcMeta.default_basis !== undefined) return funcMeta.default_basis;
      if (fieldName === "dispersion" && funcMeta.default_dispersion !== undefined) return funcMeta.default_dispersion;
    }
  }

  // ── Priority 2: FIELD_DEFINITIONS global default ──
  var fd = fieldDefs[fieldName];
  if (!fd) return "";
  var dflt = fd.default || {};
  if (typeof dflt === "object" && !Array.isArray(dflt)) {
    if (dflt[engine] !== undefined) return dflt[engine];
    if (dflt["*"] !== undefined) return dflt["*"];
  }
  return typeof dflt === "string" || typeof dflt === "number" ? dflt : "";
}

function getFieldOptions(catalog, fieldName, engine, functional, basis) {
  var fd = ((catalog && catalog.field_definitions) || {})[fieldName];
  if (!fd) return null;

  // ── 动态 aux_j_basis / aux_c_basis 选项 ──
  if (fieldName === "aux_j_basis" || fieldName === "aux_c_basis") {
    if (fd.options_source === "dynamic_aux_basis") {
      var auxKind = fd.aux_kind;   // "j" 或 "c"
      var fallback = (fd.per_backend || {})[engine] || [];

      // 检查 needs_aux_c：如果 functional 不需要 aux_c，返回空列表
      if (fieldName === "aux_c_basis" && functional) {
        var funcMeta = lookupCI((catalog.method_meta || {}), functional);
        if (funcMeta && !funcMeta.needs_aux_c) return [];
      }

      // 从 basis_catalog_v2 注入当前 basis 的量身定制项（v1.1: 改读 _v2 字段）
      var basisCatalog = (catalog && catalog.basis_catalog_v2) || {};
      var basisKey = "aux_" + auxKind;
      if (basis && basisCatalog[basis] && basisCatalog[basis][basisKey]) {
        var tailored = basisCatalog[basis][basisKey];
        if (fallback.indexOf(tailored) < 0) {
          return [tailored].concat(fallback);
        }
      }
      return fallback.slice();
    }
  }

  // ...其他字段保持原逻辑...
  if (fd.options) return fd.options;
  if (fd.per_backend) {
    var pb = fd.per_backend[engine];
    if (Array.isArray(pb)) return pb;
    return null;
  }
  return null;
}

15. 附录：术语表

 | 术语 | 含义

 | RI | Resolution of Identity，分辨率恒等式。用于加速双电子积分计算

 | RI-J | 仅对库仑积分使用 RI（用于普通 DFT）

 | RIJCOSX | 对库仑（RI-J）和交换（COSX）积分都使用 RI 近似（ORCA 默认推荐）

 | RIJK | 对库仑和交换积分都使用完整 RI（精度高，速度不如 RIJCOSX）

 | /J 辅助基组 | 用于 RI-J 库仑拟合的辅助基组（def2/J 是 universal）

 | /C 辅助基组 | 用于 RI-MP2/DLPNO 等波函数方法的相关拟合辅助基组

 | def2/J | Weigend universal /J 拟合基，适用于任何主基组（不限于 def2）

 | AutoAux | ORCA 关键字，自动为主基组生成辅助基组

 | 3c 复合方法 | r2SCAN-3c / PBEh-3c / B97-3c — 速度优化的"开箱即用"方法，RI/基组已固化

 | 双杂化泛函 | PWPB95 / wB97M-2 — DFT + RI-MP2 混合方法，需要 /J + /C 两套辅助基组

 | DLPNO-CCSD(T) | 域对自然轨道耦合簇方法，自带 RI 体系（auxJ/auxC）

 | composite | ri_support 三态之一：复合方法，RI 体系完全固化

 | user | ri_support 三态之一：用户可选 RI

 | automatic | ri_support 三态之一：后 HF 方法，RI 自动

 | needs_aux_c | 布尔字段：当 ri_support=user 时，是否需要 /C 辅助基组（双杂化=True）

 | v1.1 default_aux_j / default_aux_c | METHOD_META 顶层字段：替代原 basis_block template，供统一 %basis 渲染派生

 | v1.1 basis_catalog_v2 | API 顶层字段：含 aux_j/aux_c 元数据的 dict，与原 basis_catalog (array) 共存

 | v1.1 _normalize_legacy_levels | store.py 读时归一化层：把 SQLite 历史 job 的 aux_basis 在内存层转为 aux_j_basis / aux_c_basis

 | v1.1 Phase 0a 关卡 | BASIS_CATALOG 化学事实自检（ORCA 关键字存在性断言），数据层改完即跑，防止错误数据下流
