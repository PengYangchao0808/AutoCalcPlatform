# M4-05 — third-party capability plugin vertical slice (G16/G18)

Generated by `scripts/acceptance/acp2_m405.py`.

## What ran (real public path, no in-test registration)

1. `environment.json` — the committed A-22 external plugin and the A-23
   v1/v2 upgrade pair are built offline (`python -m build --wheel
   --no-isolation`) and installed into a throw-away venv with
   `--no-deps --no-index`; the wheel digests and every command are kept.
2. `enable.json` — the operator CLI (`acp science-plugin enable`) reads the
   installed fact and persists installed/enabled/enabled_by/enabled_at plus
   the descriptor digest and the **computed** distribution digest.
3. `discovery.json` — a new Controller process discovers the capability on
   `GET /api/capabilities` and `GET /api/v2/science/capabilities` (the two
   surfaces agree) and serves its third-party form on
   `GET /api/v2/science/capability-forms`.
4. `form.json` — the real Workbench modules (`resource-store`, `ui_subset`,
   `science-query`, `features/capability-form`) render the served form,
   commit the required field through the rendered control, refuse a
   numeric edit with the typed `ui_value_type` and display the real
   preflight ViewModel (plan/form/descriptor digests + bound fields +
   disabled submit with its reason).
5. `execution.json` + `product-external-v1.json` — one prepared artifact is
   analysed by the enabled capability through the plugin host; provenance
   carries `capability@version`, descriptor/form digests and the computed
   distribution digest; a tampered ref (409 `digest_mismatch`) and an
   invented capability (422 `unsupported_capability`) are refused.
6. `upgrade-install.json` + `upgrade.json` + `product-upgrade-v*.json` —
   the upgrade pair moves 1.0.0 → 2.0.0; a **new** Controller discovers
   2.0.0, the next analysis freezes the new pin and the new computed
   distribution digest, and the 1.0.0 frozen descriptor + product stay
   readable.
7. `browser/schema-form-live/` — the registered C row runs in a real
   Chromium against the real Controller: third-party form rendered from
   discovery, value typed, typed numeric refusal, real preflight response
   displayed, submit disabled with the approval reason, plus its
   `acp2.acceptance.v1` receipt, screenshots, console and network records.
8. `uninstall.json` — the distribution is removed; a new Controller no
   longer discovers it, the capability is projected `read_only` from the
   frozen descriptor, execution is refused, and the historical product
   still digest-verifies.
9. `negatives.json` — incompatible API range, unknown licence, untrusted
   capability, insufficient authorization and installed-bytes/digest
   mismatch all fail closed through the same operator/public path; the
   control installs prove the mutation caused each refusal.

## Declared boundaries

* The upstream science run is a seeded completed task row holding the
  fixture's fixed native record (`seed_completed_task`): the plugin really
  consumes a prepared artifact, but no ORCA/xTB/LSF/model process starts.
* The A-23 upgrade pair ships no UI form, so the form leg uses the A-22
  external plugin (the one that ships `cccp_ui_form.json`). Upgrade pin,
  digest and history are demonstrated on the A-23 pair.
* The Workbench has no panel for a third-party analysis *product*; the
  capability-form panel displays the preflight ViewModel and the product is
  surfaced by the analyze response and its digests.
* The browser row is the Playwright-bundled Chromium (the system Edge
  channel is exercised by the M4-02 rows on this same host).

## Findings recorded by this run

* M4-05-F1: the capability-form DOM `change` handler stores the control's
  string value verbatim, so a human edit of an integer field is refused as
  `ui_value_type` until the value is typed. The refusal is recorded in both
  the headless and the browser rows; the Workbench source is frozen by this
  task, so the row keeps the typed default for the numeric fields.
* M4-05-F2: `SciencePluginRegistry` scans installed distributions once per
  process, so an upgrade/uninstall is only observable to a **new**
  Controller process. Every upgrade/uninstall leg therefore restarts the
  service instead of assuming in-process invalidation.
* M4-05-F3: with every right-sidebar panel expanded the capability-form
  panel is squeezed to about one pixel; the browser row collapses the
  neighbouring panels with the page's own control before using the form.
  The layout itself is Workbench source and is not changed here.
* M4-05-F4: the Workbench has no panel for a third-party analysis
  product; the product is surfaced by the analyze response and its
  digests.
