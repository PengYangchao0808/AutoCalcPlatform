**What you'll get:** ACP 在并发、重启、远程升级条件下可靠执行长时间计算所需的一整套执行协议——每个任务实例都有唯一且持久的存储位置、代码版本与提交记录；用户暂停/取消不会被旧状态覆盖；远程取消与提交未决必须核对确认；恢复只复用身份与工件都有效的科学结果。

**Why this approach:** 缺陷报告把这批问题的根因归为"缺执行身份、状态转换与远程副作用确认"。因此先把状态写入改成带条件的窄更新（消灭旧写覆盖），再统一远程目录身份与提交/取消协议，然后把远端代码固定为内容摘要版本，最后重做恢复身份与断点语义，并用反转离线探针逐项验收；真实集群只做门控三态验收，不阻塞开发。

**What it will NOT do:** 不迁移底层计算库、不新增全局任务状态、不支持多结构或重复步骤的计划、不在提交结果未知时删远端目录或盲目重试、不改动任何科学算法。

**Effort:** XL
**Risk:** High - 同时触及远程执行协议、并发状态写入与断点恢复三个高风险域，靠假集群注入与并发屏障测试锁定。
**Decisions to sanity-check:** 独立成计划而不并入正在执行的迁移计划；先冻结四张共享执行契约表（提交/取消状态、attempt 与目录、结果记录与顺序、身份与兼容）再编码；多结构/重复步骤采用"明确报错"而非实现；前置条件只做最小串行模型；未决状态不加全局状态字段；远程代码用内容摘要版本目录且发布后不可写；attempt 1-based 且 rerun/continue 为原地重跑、以回执归档隔离 attempt；真实集群验收为三态门控。

## Scope
### Must have

1. **D01 远程存储身份**：任务远端目录由本地已分配存储路径（`<project_leaf>/<task_dir_name[__NN]>` 相对 `run_root`）唯一派生并在 `record.result["remote"]` 持久化；提交、脚本、拉取、恢复、清理统一消费该映射；远端首次创建排他占用、以 `job.json`/`task.json` 的 `job_id` 校验所有者；外来/无主目录冲突报错、不删除、不覆盖。continue/rerun/编辑重算复用同一存储目录（原地重跑契约；运行回执按 attempt 归档隔离，科学结果经身份校验复用）。
2. **D02 提交协议**：bsub 前持久化提交意图（attempt/node/dir/state=`intent`）；`submit_remote` 在拿到 LSF job id 后立即通过回调持久化（早于 tail/stage 操作）；异常分为"明确拒绝"（不删目录、置 FAILED）与"结果未知"（保留目录、state=`unconfirmed`、可核对、不盲目重试）；核对按唯一 LSF 作业名（脚本把 `-J` 替换为 `acp_<submission_id>`，job_id:attempt 摘要）或 job id 进行；启动恢复处理未决提交。
3. **D03 执行版本**：以文件内容摘要构建 release 清单并上传到 `remote_code_dir/releases/<release_id>`（校验完整后写 `.complete` 才可发布）；每个作业在提交时绑定确定 release，脚本 `PYTHONPATH` 指向该 release；同步不完整/未验证时拒绝新提交；`auto_sync=False` 必须选择既有已验证 release（pinned/环境变量），无则拒绝，仅显式 dev 逃生门允许共享目录并标注 unversioned；旧 release 按"任何状态引用 + 活跃 ref + retention"回收。
4. **D04 状态转换**：`jobs` 新增 `revision`/`attempt` 列；`JobStore.transition()` 条件更新（expected_status/revision/attempt）+ `JobStore.update_progress()` 窄字段更新；manager 全部状态写点改走条件转换；用户控制意图与观测状态分离，旧轮询/旧 attempt 不得覆盖新状态；进度更新绝不覆盖 status/spec/result。
5. **D05 取消确认**：CANCELLING 作为持久意图；重启/轮询对远程取消作业核对远端，必要时重发 bkill；仅确认停止后才发布 CANCELLED；通信失败保持 CANCELLING（待确认）。
6. **D06 恢复身份**：指纹 schema v2 绑定输入内容/原子顺序/角色/规范化科学参数/依赖工件摘要；路径仅作位置独立保存（同内容合法搬迁可重映射）；执行记录绑定代码 release；旧 checkpoint 显式兼容规则或保守重算并记录原因；恢复时校验所需结果工件存在且摘要匹配。
7. **V01–V03 resume 语义**：已完成事实永久保留（不再改写为 `skipped`）；每个步骤的科学结果持久化到 `step_result.json`（含 `step_identity`，恢复仅收养身份匹配且工件完整的结果）；恢复时重建完整 manifest 并仅重试发布；下游交接数据（频率日志引用、能量+单位、几何身份）持久化并可恢复。
8. **D07 计划前置条件**：在 ACP 编排层定义步骤所需输入与前置条件（几何有效性、频率日志、能量）；不满足时记录 `blocked`/`upstream_failed` 步骤级原因；**必需步骤 blocked 时整体不判 completed**；独立步骤可继续；诊断性继续必须显式声明策略并标注结果用途（`diagnostic_only`），恢复时重新检查；不引入通用 DAG。
9. **D08 计划契约约束**：`validate_plan` 拒绝多 item、重复 StepKind、非法组合（如 THERMOCHEMISTRY 缺少前置 FREQUENCY/SINGLEPOINT），错误提示使用 BatchOptimize；执行器不再静默忽略第 2 个 item 或共享覆盖同 kind 目录。

## Execution strategy
### Parallel execution waves
> 波次按"可验证的架构状态"划分；跨域波次（状态/远程/恢复）除依赖矩阵标注的硬依赖外可并行推进。Final verification wave 在全部 todo 完成后并行执行。

- **Wave 1（状态转换基础，todos 1–3）**：store CAS/窄更新 + 迁移 + manager 全部状态写点条件化。退出：probe 的 poll/pause 交错反转为 PAUSED 保持，终态不可复活，旧 attempt 不能改新 attempt；manager 零整行回写守护绿。
- **Wave 2（远程执行身份/提交/取消确认，todos 4–6）**：D01 存储身份、D02 提交协议、D05 取消确认。退出：同项目同名并发/跨项目同名/rerun/continue/旧目录残留五类远端位置断言；提交不确定性注入不清理并可核对；CANCELLING 跨重启只在确认后 CANCELLED。
- **Wave 3（执行版本，todos 7–9）**：release 模块 → 绑定/门禁 → E2E/回收。退出：内容变（mtime 不变）/删除/部分上传失败/排队升级四类断言；同步未验证拒绝提交；作业绑定不可变 release。
- **Wave 4（恢复身份与 resume 语义，todos 10–14）**：指纹 v2 → V01 → V02 → V03 → 恢复回归。退出：probe fingerprint/resume_existing_plan_coverage 全部反转为预期；三次恢复不增加已完成 QC；产品数稳定；热化学交接恢复。
- **Wave 5（计划契约，todos 15–16）**：D08 基数/重复/组合拒绝 + D07 前置条件/失败传播/诊断策略。退出：多 item/重复 kind/非法组合明确报错；依赖步骤 blocked 且独立步骤继续。

**B. attempt 与目录规则**
- **job 存储身份**：`record.work_dir` + 相对远端路径 + 所有者 job_id，跨 attempt 不变；**attempt 运行身份**：`jobs.attempt`。
- `attempt` 为 **1-based**，唯一递增来源是 scheduler（continue/rerun/编辑重算）；迁移回填旧行 `COALESCE(json_extract(result_json,'$.attempts'),1)`；`job_edit.attempt_number` 改为读列（仅旧行回退 result）。checkpoint 内部恢复计数改名 `resume_count`，与 `jobs.attempt` 分离；**v1 序列化键保持 `attempts`（冻结夹具逐字节不变）**，v2 使用 `resume_count`，`_plan_fingerprint` 保留为 legacy 别名（Oracle M7 / Momus m-2/m-5）。
- continue/rerun/编辑重算/跨节点 continue **复用同一存储目录**（路径/存储身份稳定；当前 `_inplace_requeue_locked` 即原地重跑，todo 19 修正 `{name}__rerun` 旧描述）。**逐操作执行策略（用户复核 #5 / Oracle H4 / r7 #2）**：`continue` = 复用身份有效的已完成结果；`编辑重算` = 身份匹配的步骤复用、变化步骤重算；`rerun` = **干净 attempt（强制重算，禁止收养历史结果）**。**运行回执隔离与科学结果复用分开（用户复核 r7 #2）**：(a) 所有操作都把旧 attempt 的运行回执（本地 `.exit_code`/`state.json`/`run.lock`；远端 `.exit_code`/`state.json`/`.stage_*`）归档到 `WORK/00_RUNTIME/attempts/<n>/`，新 attempt 不接受旧回执；(b) `continue`/`编辑重算` 在新 attempt 开始时写 `WORK/00_RUNTIME/resume_source.json`（含源 attempt 号、归档目录、plan/step 身份摘要），**从归档的上一 attempt `checkpoint.json`/`step_result.json` 读取科学结果**，逐条通过身份与工件校验后复用，活跃目录只写本 attempt 的新结果；`rerun` 不写 resume_source、不读取归档，旧结果仅留档；(c) 被复用结果保留原始执行 attempt，另记 `reused_from_attempt`。归档失败则中止提交并标记该 attempt 不可续（**不得回退为删除**）。**远端归档位置/时序（Oracle H5）**：远端回执归档由**提交线程在 bsub 之前**执行（与 claim 同前置门禁）；归档失败即中止提交；归档完成前不进入 PENDING，poller 不得观察到该目录。**存储身份跨 attempt 保留（Oracle H4）**：requeue 必须保留 `result["remote"]`/`result["remote_dir"]` 等存储身份字段，只清除本次提交相关字段（`remote_job_id`/`submit_state`/`cancel_state`/旧 attempt 回执），不得像现状那样把整个 `result` 重置为 `{"attempts","attempt_history"}`。
- **任何提交（新建或复用）都不做整目录删除**（**精确口径见下方统一谓词：仅"本 attempt 新建（created）"的目录可在准备失败时经 `_cleanup_remote_dir` 清理；复用目录永不整删**）：`not_accepted` 也不删除（由 retention 回收）；只允许清理明显属于本 attempt 的临时 staging。**`_cleanup_remote_dir` 必须门控（Oracle r16 P3 / r17 P3-Major）**：`remote/runner.py:234,713` 的 `_cleanup_remote_dir` 仅在**本 attempt 首次成功 claim（fresh claim）**后、且确认目录归属本 attempt 时才可删除；**复用的目录（continue/rerun/编辑重算）上不得调用 `remove_remote_dir`**（`sftp.py:243-259`），避免误删上一 attempt 的 checkpoint/step_result/RESULT。**统一删除谓词与 claim 处置透传（Oracle r17 P3）**：`claim_remote_job_dir` 必须**返回处置 `created` | `reused`**（`sftp.py` 新增），并透传至 `_cleanup_remote_dir`；**唯一删除谓词**：`deletable = (claim disposition == created) ∧ ownership == self ∧ never reused`——即**只有本 attempt 新建的目录**可在准备失败时清理；`except Exception`（`:234`/`:713`）在 claim 成功但**属复用目录**、或后续晚失败时**不得删除**（目录须字节不变）；契约 B 的"任何提交不做整目录删除"与"清理新目录"以此谓词统一，消除表-与-待办冲突。

**C. 科学结果记录与持久化顺序**
- `step_result.json` 必含：`schema_version`、`step_identity`（该步通用+任务专属有效参数 + 实际输入内容 + 依赖工件摘要；用户复核 r7 #1/#3）、稳定 `step_id`（含稳定性节点）、`job_id`/`attempt`/`code_release`、结果字段、artifacts（path+sha256）、依赖工件内容摘要；被复用时另记 `reused_from_attempt`。

- checkpoint 缺失/不匹配或 `plan_identity` 变化时：仍按 `step_identity` **逐步**收养匹配且 artifacts 完整（存在+摘要一致）的结果（末步变化只重算末步；上游变化使依赖步骤的 `step_identity` 失效）；否则重算并记录原因（用户复核 r7 #3）。`continue`/`编辑重算` 的复用来源是 `resume_source.json` 指向的归档 attempt（见共享契约 B），不是被清空的活跃目录。

**D. 身份与兼容规则**
- **两层身份（用户复核 r7 #1/#3）**：`plan_identity` = 步骤序列/每步 spec 结构/items 的规范化摘要（绑定整个 checkpoint）；`step_identity` = 该步**通用有效参数**（`ResolvedCalculationSpec`：method/basis/dispersion/RI/aux/solvent/grid/SCF 等）+ **任务专属有效参数**（来自实际执行使用的规范化请求：scan 坐标/点数/模式、optimize 约束/TS/信任域、IRC directions、CASSCF active space 等；`resolve_effective_params`/`ResolvedCalculationSpec` **不保留**这些字段，必须由 ACP 侧从实际派发的规范化请求显式纳入，用户复核 r7 #1）+ 实际输入内容/原子顺序/角色 + 依赖工件内容摘要。文件路径不参与哈希（内容摘要表示，位置单独保存）。`plan_identity` 变化可拒绝整体 checkpoint，但 step_result 只要 `step_identity` 匹配即可被逐步收养。
- attempt 元数据（不入科学哈希）：`code_release`、`config_digest`、软件版本；恢复时 `config_digest` 不一致 → 保守重算。
- v1（legacy）checkpoint：**默认保守重算**（事件 `identity_unverifiable_legacy`）；仅当显式启用兼容开关且输入 mtime 不晚于 checkpoint 且已完成步骤工件齐全时才可复用，并记录依据。
