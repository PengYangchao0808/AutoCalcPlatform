# acp-architecture-acceptance-remediation - Work Plan

## TL;DR (For humans)

**Who this is for and what changes for them:** For ACP researchers and operators, a failed run will stop looking successful, a rerun will be visibly a new execution, local and remote prepared results will read correctly, ordinary submissions will use the new worker chain, and the NMR/vibration views will render on first use. Maintainers and reviewers get per-defect proof instead of a green suite that hides known faults.

**What you'll get:** The twelve code/test defects from the acceptance report and the missing default worker chain, fixed in dependency order, each with its original counterexample turned into a permanent test. A new acceptance report records what actually passed, what failed, and what could not be verified because the environment was absent.

**Why this approach:** Truth and identity come first. A false success, a stale receipt or a wrong attempt makes every later "completion" meaningless, so those are fixed before the default chain and before any acceptance claim. The existing selectors, compatibility surfaces and scientific contracts are reused rather than rebuilt.

**What it will NOT do:** It will not build the deferred capabilities (identity/quota wiring, MCP, project packages, metering, persistent events, frontend prepare consumption), will not rebuild the architecture, will not delete compatibility paths or assets, will not restart or release the service, and will not turn an unexecuted environment into a pass.

**Effort:** XL
**Risk:** High - execution identity, prepare semantics and the default worker chain are cross-layer and easy to get subtly wrong.

**Decisions to sanity-check:** The default worker chain is delivered in full but activated narrowly: only `singlepoint` is default at first, and each other workflow is added only after its request/publication/recovery evidence. The local worker runs from an immutable verified release, not a cached hash of a mutable checkout. Prepare identity is located by the expected content identity/generation/binding, not the last-created row. Publication is persisted as pending with the terminal CAS so a crash after the CAS resumes publication without recomputing QC. A stale/foreign receipt never changes the current job, while a current corrupt receipt produces exactly one CAS failure. Environment-dependent science/LSF/packaging cells stay `NOT_VERIFIED` rather than being guessed, with code-delivery gaps and environment gaps reported separately.

## Scope

### Affected user and ideal state

The affected users are (a) ACP researchers/operators, including remote LSF submitters, who submit through GUI/CLI and rely on status, results and reruns; (b) maintainers and acceptance reviewers who rely on receipts, tests and evidence; (c) consumers of the CCCP library, Services worker and Web bundle; (d) frontend users inspecting NMR/vibrational results; (e) consumers of the retained old GET endpoints and the seven legacy workflows during the compatibility window.

| Row | Statement | Reason |
| --- | --- | --- |
| IS-1 | A failed, cancelled or blocked scientific run is never reported as success in task status, receipt or process exit code, and downstream steps do not consume it as valid. | A false success corrupts every downstream scientific and recovery decision. |
| IS-2 | A receipt is reused only when its full frozen execution identity matches the current envelope; conflicts are rejected, preserved and surfaced as non-zero failure. | Reruns, parallel workers and restarts must never report another attempt's success. |
| IS-3 | Task detail/list/recovery/v2 projections and the frontend expose the authoritative attempt and record revision, so a rerun invalidates the old result session. | Users must see which execution produced what; stale UI hides real reruns. |
| IS-4 | Prepared reads serve local work_dir originals and remote cached copies with authorization, path and size bounds; availability distinguishes ready/preparing/failed/absent without fetching, enqueueing or parsing. | The common local case and the remote case must both work without hidden side effects. |
| IS-5 | Prepare operations dedupe by full content identity; generation/digest/binding/authorization changes create a new operation, and an evicted success can be explicitly re-prepared. | A cache rebuild must not be swallowed by an old success record. |
| IS-6 | Production prepare execution remains bound to the frozen lease attempt/content/generation/binding/authorization; an old attempt can never mark a new attempt's resource ready. | Restart and rerun races must not publish stale bytes as current. |
| IS-7 | An ordinary submission of a declared workflow automatically freezes envelope/plan/binding, dispatches the Services worker, verifies the receipt, advances via CAS and publishes; legacy remains only for undeclared/disabled workflows. | The delivered capability must be the default path, not a test-only selector. |
| IS-8 | NMR and vibrational visualizations render correctly on first use, preserve live instances/canvas, support export and multi-instance teardown. | These are user-facing scientific views; a blank canvas or invisible arrows is a lost result. |
| IS-9 | Bounded/derived product identity includes the full source scientific identity (generator/algorithm/version/params/schema), so no two different sources collide in cache or recovery keys. | Scientific reuse keys must be collision-free. |
| IS-10 | Every defect closes against its original counterexample and a frozen candidate is re-accepted with explicit PASS/FAIL/NOT_VERIFIED per gate. | The existing FAIL report must be superseded by new evidence, not by assertion. |
| IS-11 | Touched quality roots are lint/format clean, compatibility shims/assets/fixtures remain, and deferred capabilities are handed off with owners and entry conditions. | The fix must not create new debt or silently expand scope. |
| IS-12 | Old GET endpoints and the seven legacy workflows keep their current behavior and fallback semantics throughout the compatibility window; no one deletes them to make the new path look complete. | Existing users and historical tasks must not break while the new paths are introduced. |
| IS-13 | A publication failure keeps the valid scientific result and retries publication only; it never recomputes QC or reports a complete product prematurely. | Expensive science must not be repeated because a manifest write failed. |
| IS-14 | Each attempt selects exactly one execution entry and never dispatches legacy and Services workers simultaneously; an unknown remote submission is reconciled before any retry. | Double dispatch and blind retry would corrupt attempt identity. |

## Verification strategy

> Zero human intervention - all verification is agent-executed.

- Test decision: **regression-first** (port the original counterexamples into formal tests before or with the fix) plus **tests-after** for new behavior (D07 freeze/completion, D05 content identity, D04 root routing, D08/D09 browser behavior). Frameworks: pytest, the zero-dependency Node harness `frontend/js/module_tests/run_all.js`, and Playwright Chromium with the repository `3Dmol-2.5.5.min.js`.
- Evidence: `.omo/evidence/acp-architecture-acceptance-remediation/task-<N>-acp-architecture-acceptance-remediation.md` plus raw logs named in each todo. Product-facing evidence is committed under `reports/architecture_remediation_20261020/`; `.omo/evidence/` stays as the working ledger.
- Every todo's acceptance criterion must be executable by an agent: an exact pytest/node/ruff/compileall invocation with a concrete assertion, not "inspect" or "verify manually".
- Environment-dependent cells (real ORCA/CREST/xTB/CENSO, real LSF/SSH/SFTP, frozen F0/S0 bundles) are executed only when the binaries/config/credentials are present. Absent environment records `NOT_VERIFIED` with the skip reason; it is never counted as PASS.
- Evidence vocabulary is the source plan §2.3 vocabulary: `PASS / FAIL / NOT_VERIFIED` plus scope `IN_SCOPE / DEFERRED / NOT_APPLICABLE`. An executed failure may never be relabeled `NOT_VERIFIED`; `DEFERRED` is never `PASS`; every skip is explained individually. The report uses the task-status vocabulary `待实施 / 实施中 / 待复验 / 已关闭` where a defect status is needed.
- False-pass guards: a green Node suite does not prove D08/D09 (the old suite contained "recorded finding" fault assertions); `browser_probe.py` exit code 0 is never a pass (it is diagnostics only); a generated remote command string or a mock-paramiko call is never real LSF; a TestClient is never F0; a new service's retained old route is never S0; a skip is never real-environment PASS.
- Test environment: install with `pip install -e '.[dev,api,remote,browser]'` and `python3.11 -m playwright install chromium` for the browser gates; new runtime imports must be added to `requirements-node.txt` and `pyproject.toml` in the same change, and tests must not depend on undeclared redacted-host packages. If the browser extra/Chromium cannot be installed, the G5 browser cells are recorded `NOT_VERIFIED`, not skipped silently.
- Failure scenarios are mandatory for identity-sensitive work: stale attempt, changed release/digest/owner/fencing, corrupt receipt, cancellation during prepare, rerun during transfer, cache eviction, restart, duplicate delivery, concurrent enqueue/claim, and old-row compatibility.
- Concurrency/crash proofs are mandatory for D07: two real workers racing at "no receipt" must execute once; a killed group writer must never expose a mixed envelope/plan/binding; a barrier after the last identity check and before publish must block a late rerun/rebind/revoke/evict; a process killed after terminal CAS but before publisher must resume publication on restart without a second QC run.
- Release/activation discipline: the local child must load from a verified immutable release path (assert the real module path/digest), not a cached hash of a mutable checkout. Scientific closure (`ENABLED_WORKFLOWS`) is separate from default activation (`DEFAULT_ENVELOPE_WORKFLOWS`); only singlepoint starts active and each other workflow is added after its own request/publication/recovery evidence.
- Code candidate vs evidence-only: freeze the code candidate SHA after all implementation/tests/harnesses are integrated; the final report records the code SHA and an evidence-only report SHA. Any code change after freeze re-runs the affected gates; only evidence-only edits may reuse the candidate SHA.
- Historical probes are audit artifacts: preserve their hash and original result, but do not require an unchanged probe setup to remain valid after a contract change. Formal tests keep the original defect trigger and adapt the fixture/provider/entry to the new public contract; an expected interface difference is recorded with its formal-test mapping and is never labeled PASS or NOT_VERIFIED.
