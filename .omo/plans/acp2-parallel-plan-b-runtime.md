# acp2-parallel-plan-b-runtime - Work Plan

## TL;DR (For humans)

**Who this is for and what changes for them:** The B-track operator gets a decision-complete execution plan; researchers and lab operators get one Controller whose CLI, HTTP and MCP/Agent entries see the same task, attempt and artifact; A and C get frozen runtime contracts they can build against without reading B's working tree.

**What you'll get:** A contract-first ACP 2.0 Plan B execution: a real stdio MCP entry, persistent cross-process idempotency, server-enforced admission, real Local and LSF singlepoint evidence, artifact prepare/read, approval and budget facts, event/recovery contracts, infrastructure adapters, migration/backup proof, and an installable release candidate.

**Why this approach:** Plan B is a 27-source-task, 33-todo, H0-H7 gated program, not a single feature. The load-bearing decisions are: freeze contracts and the acceptance harness before consumers exist; make the MCP process a transport adapter over one loopback HTTP Controller instead of a second manager; put idempotency in the same SQLite transaction as job creation; keep approvals and budgets as separate persistent facts.

**What it will NOT do:** No second Controller, second task state machine or new `JobStatus`; no science logic in the B/platform layer; no fake PASS from mocks, `--dry-run` or module tests; no production `acp.service` restart or release without separate authorization.

**Effort:** XL
**Risk:** High - real ORCA/LSF/DSH execution and cross-process restart semantics are the main failure modes; missing environments must remain `NOT_VERIFIED`.

**Decisions to sanity-check:** The batch is the full H0-H7 program advanced by evidence gates, matching A/C; only ADR-005 licensing, ADR-008 scientific acceptance and production deployment remain user decisions. The MCP adapter talks HTTP to the one Controller; idempotency is persisted in the jobs DB transaction; approvals use a new table, never `WAITING_REVIEW`; packaging closes the debug report's `G4 OPEN` with separate CCCP-only/worker/Web configs.

## Verification strategy

> Automated checks are agent-executed; scientific approvals and independent reproduction are recorded by their named owners, not inferred from the automation.

- **Test decision:** contract-first + TDD for new pure modules (`acp2_runtime.py` harness, contract validators, idempotency store, approvals, adapter registry); tests-after for wiring where the contract already exists (MCP bindings, routes, admission/receipt hooks); real-environment acceptance is gated and never replaced by unit tests.
- **Project evidence root:** absolute `$ACP2_EVIDENCE` = `reports/acp2_implementation/<candidate-label>/`; every run writes an immutable `owner/task/subtask/run_id/` directory and `B/Bxx/` is the B task view. `integration/` stores references, never overwrites. The start label is `final_debug_candidate`'s short SHA; every new frozen candidate gets a new label, and a PASS may be reused only by explicit mapping to the same unchanged code/dependency/config combination. Every receipt carries task ID, `candidate_revision`, `contract_version`, exact argv/cwd, exit code, start/finish, assertions, result/reason, artifact relative paths + SHA-256, and `job_id/attempt/release/submission_id` for science jobs.
- **ulw-loop evidence:** each todo also writes `.omo/evidence/task-<N>-acp2-parallel-plan-b-runtime.md` with the executed command lines and the project evidence path.
- **Vocabulary:** `PASS / FAIL / NOT_VERIFIED` plus `IN_SCOPE / DEFERRED / NOT_APPLICABLE` in separate columns. Missing prerequisites are `NOT_VERIFIED`; an executed assertion failure is `FAIL`; `DEFERRED` is never a PASS.
- **Readiness ladder (R3-03/R3-10):** every contract, module and integration row carries `contract_ready -> implementation_ready -> integration_ready -> verified`. Static contracts, fixtures and component work may proceed at `contract_ready`/`implementation_ready` without real science; only `verified` closes a stage row. A missing external environment keeps the live row `NOT_VERIFIED` without blocking independent work.
- **Command completion (R3-14):** every evidence command must be runnable as written. A literal `...` in a command is a usage error (exit 3), not a placeholder for the executor; substitute the absolute fixture/output/controller values from `acceptance-env.sh` before recording evidence. `--help`/`--dry-run`/`--check-only` remain tool checks, not scenario PASS.
- **Early package smoke (R3-14):** P0/P1 build a minimal CCCP wheel, worker-role install and Web/static sample outside the repo, checking top-level file ownership, inter-package dependency constraints, install/upgrade/uninstall, NMR assets/notice/static locations and import without external QC binaries. The full role packages, complete assets and independent reproduction remain B25/P5.
- **Evidence reuse (R3-14/D09):** record `source_candidate`, `client_revision`, `harness_revision`, `evidence_revision` and an explicit applicability mapping (unchanged code/dependency/config/input/validator). The final HEAD need not equal every raw receipt SHA, but every reused PASS must point to the unchanged scope; a changed input re-executes.
- **Minimum command set (run from the frozen candidate root in B's venv):**

  - `pytest tests/test_acp2_runtime_acceptance_harness.py tests/test_acp2_runtime_contracts.py -q`

  - `pytest -m "not slow" -q` at P1/P2/P4/P5 candidate freezes.

A full-repo zero-diagnostic cleanup is a separate task, never a condition of every todo, and rules/excludes may not be weakened to pass.
